# ТЕОРИЯ #

## БАЗОВЫЕ ПОНЯТИЯ ##

*Docker* - это платформа контейнеризации. Она позволяет упаковать
приложение вместе со всеми зависимостями в изолированную среду -
*контейнер*. Такой контейнер можно запустить где угодно: на локальной
машине, сервере или в облаке, и результат всегда будет одинаковым.

Отличие от ВМ: *виртуальная машина* имитирует отдельный компьютер со
своей ОС, драйверами и файловой системой, что тяжело, занимает много
места, требует больше времени для развертки и обработки, сильно
нагружает систему. *Контейнер* запускается на другом уровне, без своей
ОС, деля ядро хостовой ОС, но имея свое пр-во процессов, файлов и сетей.

Зачем нужен Docker:

1. *Стабильное окружение* - Docker гарантирует, что приложение будет
    работать одинаково везде. Все, что нужно для запуска, уже собрано в
    контейнер, поэтому код не зависит от различий в системах и
    настройках.

2. *Легкость и скорость* - контейнеры используют общее ядро ОС и не
    создают отдельную копию ОС, за счет чего занимают меньше места и
    быстрее запускаются.

3. *Масштабирование* - при росте нагрузки можно просто запустить доп.
    контейнеры для увеличения мощности и перераспределения ресурсов.

4. *Изоляция процессов* - каждый контейнер работает независимо от
    других.

5. *Удобная интеграция в CI/CD*.
________________________________________________________________________

Основная система - *Docker Engine*. Состоит из:

- CLI для общих команд от поль-ля.

- *dockerd* (Docker Daemon) - демон, выполняющий все реальные действия
    (создание, запуск, удаление контейнера).
    
    Сам дополняется с:

    - *containerd* - отвечает за жизненный цикл контейнеров - создание,
        запуск, остановку и удаление. Т.о. запущенные контейнеры
        отцепляются от dockerd и зависят от работы уже сугубо
        containerd.

    - *runc* - делает сам запуск контейнера: изолирует процессы и
        исп-ет механизмы ядра Linux, которые отвечают за изоляцию и
        контроль ресурсов.

        - *namespaces* - отвечают за изоляцию. Они создают для каждого
            контейнера отдельное пр-во процессов, поль-лей, сети и
            файловой системы. Контейнер видит только свое и не может
            напрямую взаимодействовать с хостом.
        - *cgroups* - отвечают за контроль ресурсов. Они задают, сколько
            CPU, оперативной памяти и дисковых операций контейнер может
            исп-ть. Если приложение начнет потреблять слишком много,
            cgroups ограничат его, не давая перегрузить систему или
            повлиять на др. контейнеры.

- REST API для команд управления dockerd.

Архитектура следует стандартам *OCI* (Open Container Initiative) - это
набор правил, которые определяют формат контейнеров и способы их
запуска. Благодаря этому Docker совместим с др. инструментами
контейнеризации и предсказуемо работает в разных средах.

В Linux Docker Engine работает напрямую как системный демон, но в
Windows и macOS так не получится - нужна программа Docker Desktop для
создание легковесной ВМ с Linux, где уже и будут разворачиваться Docker
Engine и контейнеры. При этом весь функционал, CLI и REST API доступен
из ОС, не нужно лезть внутрь ВМ.
________________________________________________________________________

Основные определения:

- *Образ* (Image) - это шаблон, из которого  запускаются контейнеры. В
    нем уже есть все, что нужно приложению: системные библиотеки,
    зав-ти, код и настройки. Образ не меняется - Docker использует его
    как основу и добавляет поверх слой, куда попадают изменения,
    сделанные во время работы.

- *Контейнер* (Container) - это изолированная среда, в которой работает
    приложение. Контейнер можно запускать, останавливать и удалять, не
    затрагивая исходный образ. Когда он удаляется, его данные исчезают -
    поэтому для постоянного хранения исп-ют тома и монтирование.

- *Том* (Volume) - это место для данных, которые должны сохраняться м/
    перезапусками. Тома подключаются к контейнерам как внешние диски:
    все, что записано в них, остается даже после удаления контейнера.

- *Сеть* (Network) - отвечает за взаимодействие контейнеров между собой
    и с внешним миром. Docker автоматически создает bridge-сеть, где
    каждый контейнер получает свой IP-адрес. Можно объединять контейнеры
    в собственные сети или, наоборот, изолировать их, если требуется
    полная автономность.

- *Реестр* (Registry) - это место, где хранятся Docker-образы. Публичный
    вариант - Docker Hub. Для ограниченного доступа - разворачивают
    собственный Docker Registry.

## ОБРАЗЫ ##

Контейнеры запускаются из образов (image) - шаблонов, в которых уже
собраны все зав-ти, библиотеки и настройки, нужные приложению. Образ
состоит из слоев, и каждый слой - это отдельный шаг сборки: установка
пакета, копирование файлов, настройка окружения.

Образ состоит из манифеста и набора слоев.

Манифест (Dockerfile) - инструкция по сборке (из каких слоев и как).
Слои же хранятся отдельно как архивы с идентификатором sha256. При
загрузке или скачивании Docker проверяет, не были ли повреждены файлы
образа, с помощью контрольных сумм sha256.

У образа есть хэш-номер sha256, уникальный для контекретной версии
конктерного образа, и может быть тег (например, latest, dev, v1.0) для
более удобного распознавания человеком.
________________________________________________________________________

При сборке Docker складывает слои в определенном порядке и объединяет их
в единую файловую систему с помощью драйвера *overlay2*. Он накладывает
слои друг на друга так, что контейнер видит их как один диск, хотя
физически это отдельные части.

Главное преимущество такого подхода - повторное исп-е слоев. Если два
образа исп-ют один и тот же базовый слой, Docker хранит его на диске
только в одном экземпляре.

Помимо этого, послойный подход упрощает сборку ч/ кэширование. Когда
Docker собирает образ из Dockerfile, он проходит инструкции сверху вниз
и создает слой для каждой из них, после чего ситуацию кэширует. Если
потом входные данные (в т.ч. предыдущие слои) до какого-то момента будут
идентичны данному, то сборка подтянется из кэша и продолжится послойно
далее с точки различий с кэшом.

Т.о. порядок в Dockerfile важен, и чем чаще слой меняется, тем позднее
он должен объявляться.

Например:

```
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
```

В примере код добавляется в последний момент, поэтому в условиях
разработки пересборка контейнера будет только по слою кода, а остальное
подтянется из кэша.

## СЕТЬ, ЛОГИ, БЕЗОПАСНОСТЬ ##

При запуске Docker автоматически подключает контейнер к внутренней
вирт. сети. По умолчанию используется bridge-сеть - изолированная среда,
где каждый контейнер получает свой IP-адрес и может обмениваться данными
с др. участниками этой сети. Bridge-сеть создается на стороне хоста:
Docker поднимает вирт. интерфейс, назначает подсеть и настраивает NAT,
чтобы контейнеры могли выходить в интернет. 

В поль-их bridge-сетях Docker поднимает встроенный DNS-сервер. Благодаря
этому контейнеры могут обращаться друг к другу по имени, а не по IP.

Если приложению нужно принимать запросы извне, при запуске указывают
флаг -p, чтобы пробросить порт хоста внутрь контейнера.

Кроме стандартной сети есть и другие режимы:

- *host* - контейнер работает в сетевом пр-ве хоста и исп-ет его
    IP-адрес и интерфейсы. Режим без изоляции, зато с макс.
    производительностью. Подходит, если сервису нужен прямой доступ к
    сети.
- *none* - сеть полностью отключена. Контейнер не получает IP, не
    выходит в интернет и не принимает входящие запросы. Подходит для
    задач, которые работают изолированно и не исп-ют сеть. 
- *overlay* - объединяет контейнеры, запущенные на разных машинах, в
    одну вирт. сеть. Такой тип исп-ся, когда приложение развернуто на
    нескольких серверах и между ними нужно наладить связь.
- *macvlan* - каждому контейнеру назначается собственный MAC-адрес, и в
    лок. сети он виден как отдельное уст-во. Это удобно для тест-я
    сетевых сервисов или если контейнер должен работать наравне с др.
    машинами.
________________________________________________________________________

Драйвер логирования перехватывает все направленнное в stdout и stderr
внутри контейнера, собирает и хранит все.

Драйверы логирования:

- *json-file* (по умолчанию) - на хосте в формате JSON. Удобно для лок.
    отладки, но в проде обычно исп-ся драйверы ниже.
- *journald* - в системный журнал Linux.
- *syslog* - на внешний сервер.
- *fluentd* - для распределенных систем.

Помимо логов Docker фиксирует события. Удобно для мониторинга и
интеграций.
________________________________________________________________________

Для безопасности Docker исп-т разные вещи:

- *namespaces* и *cgroups* - описаны ранее.
- *Capabilities* - система тонкой настройки прав. Она ограничивает
    возм-ти root-поль-ля внутри контейнера. Например, процесс может
    записывать файлы, но не может менять сетевые настройки.
- *AppArmor* и *SELinux* - инструменты контроля доступа. Они определяют,
    какие файлы и операции разрешены процессам контейнера.
- *seccomp* - фильтр системных вызовов, который блокирует потенциально
    опасные обращения к ядру, например попытки загрузить модули или
    изменить сетевые интерфейсы.

Для доп. защиты Docker можно запустить в rootless-режиме - тогда
контейнеры работают не от имени администратора, а под обычным поль-лем.
Функ-ти чуть меньше, зато риск для хоста минимален.
