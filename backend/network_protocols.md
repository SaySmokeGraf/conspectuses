# ОБЩАЯ ТЕОРИЯ #

*Сетевой протокол* - это набор правил, определяющий принципы взаимод-я
уст-в в сети. Чтобы отправка и получение информации прошли успешно, все
устройства-участники процесса должны принимать условия протокола и
следовать им. В сети их поддержка встраивается или в аппаратную часть (в
"железо"), или в программную часть (в код системы), или в обе части.

Для взаимод-я протоколов м/ собой сущ-ют разные модели, основные из
которых OSI и TCP/IP.
________________________________________________________________________

Термины:

- *Инкапсуляция* - процесс перехода данных в биты.
- *Декапсуляция* - процесс, обратный инкапсуляции.
- *ADU* (Application Data Unit) - пакет данных целиком.
- *PDU* (Protocol Data Unit) - основная часть пакета, передаваемого по
    к-л протоколу.
________________________________________________________________________

## МОДЕЛЬ OSI ##

*OSI* (Open Systems Interconnection) основана на принципе разделения
коммуникационной системы на семь отдельных уровней. Cамым верхним
является седьмой (прикладной), а самым нижним - первый (физический).
________________________________________________________________________

Все семь уровней модели OSI можно условно разделить на две группы:

- Media Layers (уровни среды).
- Host Layers (уровни хоста).

Уровни группы Media Layers (1-3) занимаются передачей информации (по
кабелю или б/п сети) и исп-ся сетевыми уст-вами. Уровни группы Host
Layers (4-7) исп-ся непосредственно на уст-вах, т.е. компьютерах или
мобильных уст-вах.

Уровни:

1. *Физический* - отвечает за обмен физ. сигналами м/ физ. уст-вами
    ("железом") в виде бит. За этот уровень отвечают кабеля или б/п
    способы связи наподобие Wi-Fi, 4G, Bluetooth и т.д.

2. *Канальный* - для адресации в сетях. Канальный уровень получает биты
    и превращает их в кадры (frame, также "фреймы"). Задача здесь -
    сформировать кадры с адресом отправителя и получателя, после чего
    отправить их по сети. У канального уровня есть два подуровня - это
    MAC и LLC.
    
    - MAC (Media Access Control, контроль доступа к среде) - отвечает за
        присвоение физических MAC-адресов.
    - LLC (Logical Link Control, контроль логической связи) - занимается
        проверкой и исправлением данных, управляет их передачей. Хотя,
        если быть точными, LLC нельзя отнести полностью ни к первому,
        ни ко второму уровню - он между.
    
    Основной протокол - ARP (Address Resolution Protocol - протокол
    определения адреса). С помощью него 64-битные MAC-адреса
    сопоставляются с 32-битными IP-адресами и наоборот.

3. *Сетевой* - для маршрутизации, т.е. построения маршрута от одного
    уст-ва к др. с исп-ем MAC-адресов и учетом всех потенц. неполадок в
    сети. Для обеспечения этого уровня сущ-ют уст-ва - маршрутизаторы.

4. *Транспортный* - уровень, отвечающий за транспортировку пакетов. По
    сути является посредником м/ Media Layers и Host Layers. К этому
    уровню относятся протоколы TCP и UDP.

5. *Сеансовый* - первый уровень, который оперирует уже чистыми данными,
    а не набором битов. Отвечает за поддержку сеанса или сессии связи,
    управляет взаимод-ем м/ приложениями, открывает возм-ти
    синхронизации задач, завершения сеанса, обмена информации.

6. *Представления данных* - отвечает за преобразование протоколов и
    кодирование/декодирование данных.

7. *Прикладной* (приложений) - то, с чем взаимод-ют поль-ли. Все услуги,
    получаемые седьмым уровнем от других, исп-ся для доставки данных до
    поль-ля. Протоколам седьмого уровня не требуется обесп-ть
    маршрутизацию или гарантировать доставку данных, когда об этом уже
    позаботились предыдущие шесть. Задача седьмого уровня - исп-ть свои
    протоколы, чтобы поль-ль увидел данные в понятном ему виде.
________________________________________________________________________

OSI имеет ряд недостатков как модель:

- Несоответствие реальности - это можно заметить по вещам, находящимся
    м/ уровнями, и расплывчатым понятиям.
- Плохая технология - уровни часто дублируют другу друга, ф-ции
    распределены по уровням неравнозначно, а одни и те же задачи могут
    быть решены на разных уровнях.
- Кроме того, долгая разработка модели и плохое взаимод-е с
    общественностью сыграло огромную роль в популярности модели, и пока
    она разрабатывалась, на рынке установил свое превосходство TCP/IP.

Из-за этого вне сетевых технологий OSI скорее является громоздкой
моделью, где-то - идеалистической, а где-то - необоснованно запутанной.
Поэтому обычно люди пользуются моделью TCP/IP. Но при работе с сетевой
коммутацией и иногда с др. сетевыми технологиями исп-ся модель OSI.
________________________________________________________________________

## МОДЕЛЬ TCP/IP ##

*Стек протоколов TCP/IP* - модель взаимод-я протоколов связи, широко
используемая и лежащая в основе сети Интернет. В отличие от OSI,
содержит в себе четыре уровня.
________________________________________________________________________

Уровни:

1. *Канальный* - определяет то, как происходит обмен информацией на
    уровне сетевых уст-в, как информация будет передаваться от одного
    уст-ва к другому. Информация здесь кодируется, делится на пакеты и
    отправляется по нужному каналу, т.е. среде передачи. Основным
    протоколом (или скорее стандартом организации) является Ethernet.

2. *Межсетевой* - для обеспечения взаимод-я сетей м/ собой. Локальные
    сети по всему миру объединены в глобальную, а передачу данных м/
    этими сетями осуществляют магистральные и пограничные
    маршрутизаторы. Основной протокол - IP.

3. *Транспортный* - служит для обеспечения доставки информации. Основные
    протоколы - TCP и UDP.

4. *Прикладной* - для взаимодействия между пользователем и остальными
    уровнями, представления данных в понятном и возможном к исп-ю и
    интерпретации виде. Здесь есть мн-во протоколов наподобие HTTP, FTP,
    SMTP и т.д.
________________________________________________________________________

# ПРОТОКОЛЫ СВЯЗИ #

## КАНАЛЬНЫЙ УРОВЕНЬ ##

*MAC* (Media/Medium Access Control) - управление доступом к среде.
Отвечает за адресацию посредством MAC-адресов - 48-битных
идентификаторов, присваиваемых устр-вам на заводе-изготовителе. Кроме
того, осуществляет контроль множественного доступа к каналу, что
позволяет нескольким устр-вам в одной сети разделять одну среду передачи
данных.
________________________________________________________________________

*Ethernet* - стандарт организации локальных сетей (LAN - Local Area
Network, WAN - Wide Area Network) с помощью проводных соединений.
Обеспечивает надежную и высокопроизводительную среду для передачи кадров
данных. Адресация производится посредством MAC-адресов.

Основными преимуществами являются: высокая надежность, безопасность и
производительность за счет исп-я проводного типа подключения; а также
низкая стоимость и высокая доступность.

В TCP/IP относится к канальному уровню, в OSI - к физическому и
канальному одновременно. От физической части - кодирование/декодирование
сигнала 1/0 в высокий/низкий электрический сигнал. От канальной части -
ответственность за формирование из сырого потока битов кадров данных.
________________________________________________________________________

*Wi-Fi* - семейство протоколов для организации беспроводной сети.
Работает по аналогии с Ethernet, но не с эл. сигналом в кабеле, а с
радиоволнами. Отсюда меньшая надежность и производительность, но большее
удобство и покрытие.
________________________________________________________________________

*PPP* (Point-to-Point) - двухточечный протокол. Не столько относится к
канальному уровню, как находится м/ канальным и межстетевым уровнями.
Применяется для коммуникации м/ двумя маршрутизаторами без участия хоста
или к-л сетевой структуры в промежутке. При необх-ти PPP обеспечивает
аутентификацию, шифрование, а также сжатие данных. Он широко исп-ся при
построении физических сетей (кабельных телефонных, сотовых и т.д.).

У PPP есть два подвида - PPPoE (PPP по Ethernet) и PPPoA (PPP через
асинхронный способ передачи данных - ATM), интернет-провайдеры часто их
исп-ют для DSL соединений.
________________________________________________________________________

## МЕЖСЕТЕВОЙ УРОВЕНЬ ##

### <u> IP </u> ###

*IP* (Internet Protocol) - протокол Интернета. Предназначен для
маршрутизации запросов и по своей сути крайне прост - адресация и
передача без к-л контроля целостности.
________________________________________________________________________

Над передаваемыми данными надстраивает заголовок, состоящий сугубо из
адреса получателя. В зав-ти от версии имеет разный размер:

- *IPv4* - 32-битный адрес, разбитый на 4 октета. Исп-ся по умолчанию,
    отличается простотой и малым размером, но при этом ограниченностью
    адресов - всего 2^32, или чуть меньше 4.3 миллиардов. При этом их
    на самом деле много меньше.

    Первый октет отвечает за класс сети, один из 5. Вторые два октета
    отвечают за номер подсети, а последний октет - за номер конечного
    устр-ва в подсети.

- *IPv6* - 128-битный адрес, разбитый на 8 блоков по 4 шестнадцатеричных
    числа. Больше размер, что решает проблему с нехваткой вакантных
    адресов.
________________________________________________________________________

Важно также определить понятие *маска подсети*. Маска подсети помогает
маршрутизатору понять, как и куда передавать пакет. Подсетью может
являться любая сеть со своими протоколами. Маршрутизатор передает пакет
ниже (другому маршрутизатору в этой подсети или на конечное устр-во),
если маски сходятся. В ином случае пакет передается на маршрутизатор
выше.
________________________________________________________________________

### <u> Другие межсетевые протоколы </u> ###

- *ICMP* (Internet Control Message Protocol) - для передачи сообщений
    об ошибках и диагностической информации при передаче данных м/
    уст-вами.

- *OSPF* (Open Shortest Path First) - протокол поиска наилучшего
    свободного пути от исходного до конечного маршрутизатора.

- *IGMP*, *MLD* - для обнаружения и управления мультикаст-группами
    слушателей в локальной сети для IPv4 и IPv6 соотв.
________________________________________________________________________

## ТРАНСПОРТНЫЙ УРОВЕНЬ ##

### <u> TCP </u> ###

*TCP* (Transmission Control Protocol) - протокол контроля передачи.
Разбивает данные на блоки, а при приеме - собирает блоки обратно.
Протокол отличается надежностью и требуется для точной передачи данных.
Устанавливает соединение и следит, чтобы все дошло в том формате, в
котором должно быть, устраняя ошибки по ответу от принимающей стороны.
Поэтому относительно медленный.
________________________________________________________________________

Имеет следующие черты:

- *Нумерация блоков* - нужна для отслеживания дублирования или
    отсутствия блоков, а также восстановления изначальных данных в
    нужном порядке.

- *Управление потоком* - ограничение скорости и сообщение кол-ва
    передаваемых данных получателю для большего контроля за
    целостностью.

- *Контроль ошибок* - проверка байтов на целостность.

- *Порты* - исп-ся специальные порты для связи разных протоколов.
________________________________________________________________________

TCP-блок надстраивается над данными, которые нужно передать, и содержит
в себе 24 байта информации, в частности следующие эл-ты:

- Номер порта отправителя.
- Номер порта получателя.
- Номер блока.
- Номер подтверждения.
- Длина заголовка.
- Зарезервированное место.
- Флаги.
- Размер окна.
- Контрольная сумма.
- Срочный указатель.
- Опции и отступы.
________________________________________________________________________

### <u> UDP </u> ###

*UDP* (User Datagram Protocol) - протокол пользовательских датаграмм. Не
отправляет ответ о полученных данных, из-за чего менее надежен, но более
быстр, нежели TCP. Каждый блок данных в этом протоколе представляет
собой самостоятельную единицу.

Урезает все для контроля целостности, оставляя только самое необходимое,
чтобы поддерживать скорость. Исп-ся, например, при видеозвонках,
стриминге и просмотре видео онлайн, где потеря пары кадров некритична,
зато скорость передачи кадров крайне важна.
________________________________________________________________________

UDP-блок надстраивается над данными, которые нужно передать, и содержит
в себе 8 байтов информации, в частности следующие эл-ты:

- Номер порта отправителя.
- Номер порта получателя.
- Длина заголовка.
- Контрольная сумма.
________________________________________________________________________

### <u> Другие транспортные протоколы </u> ###

- *RSVP* (Resource Reservation Protocol) - для резервации приложениями
    ресурсов сети. Важен при передаче видео или звука в реальном
    времени.

- *SCTP* (Stream Control Transmission Protocol) - протокол передачи
    управления потоком. Поддерживает многоадресное соединение, позволяя
    быстро переключаться между путями.

- *RTP* (Real-time Transfer Protocol) - транспортный протокол реального
    времени. Применяется вместе с RCTP для контроля, исп-ся в
    IP-телефонии.
________________________________________________________________________

## ПРИКЛАДНОЙ УРОВЕНЬ ##

### <u> DNS </u> ###

*DNS* (Domain Name System) - словарь доменов. Связывает вписанный адрес
сайта в строку браузера и его IP-адрес.

На данный момент существуют четыре основных DNS-сервера, которые
участвуют в загрузке веб-страниц:

- DNS recursor - справочник, отвечающий за прием запросов от компьютеров
    пользователей.
- Root nameserver - корневой сервер. Является первым в процессе
    конвертации имени хоста в IP-адрес и позволяет получить список
    DNS-серверов.
- TLD nameserver - следующий шаг при поиске IP. Хранит информацию про
    все доменные имена с общим расширением (.ru, .com и т.д.).
- Authoritative nameserver - дает окончательные ответы на запросы о DNS.
________________________________________________________________________

### <u> HTTP(S) </u> ###

*HTTP(S)* (HyperText Transfer Protocol (Secured)) - протокол передачи
гипертекста. Исп-ся для передачи веб-страниц с исп-ем гиперссылок. Связь
вида "запрос-ответ".

В современности ч/ HTTP-запросы и ответы передают не только гипертекст,
но и различные данные. Т.о. данный протокол исп-ся чаще всего в условиях
передачи данных в интернете, поэтому HTTP был выделен отдельно в данном
конспекте.

HTTP занимает порт 80, HTTPS - порт 443.

HTTPS отличается от HTTP защитой данных с помощью исп-я TLS/SSL
шифрования.
________________________________________________________________________

Данные между клиентом и сервером в рамках работы протокола передаются с
помощью HTTP-сообщений. Они бывают двух видов:

- Запросы (HTTP Requests) - отправляются клиентом на сервер, чтобы
    вызвать выполнение некоторых действий. Основой запроса является
    HTTP-заголовок.
- Ответы (HTTP Responses) - сервер отправляет в ответ на клиентский
    запрос.

Само по себе сообщение представляет собой информацию в текстовом виде,
записанную в несколько строчек.

Как запросы, так и ответы имеют следующую структуру:

- Стартовая строка (start line) - исп-ся для описания версии протокола,
    метода запроса, целевого ресурса для запроса, кода ответа. Занимает
    ровно одну строчку.
- HTTP-заголовки (HTTP Headers) - несколько строчек текста в
    определенном формате, которые либо уточняют запрос, либо описывают
    содержимое тела сообщения.
- Пустая строка, которая сообщает, что все метаданные для конкретного
    запроса или ответа были отправлены.
- Опциональное тело сообщения, которое содержит данные, связанные с
    запросом, либо документ (например HTML-страницу), передаваемый в
    ответе.
________________________________________________________________________

Команды:

- *GET* - позволяет запросить некоторый конкретный ресурс. Доп. данные
    могут быть переданы через строку запроса в составе URL.

- *POST* - позволяет отправить данные на сервер. Поддерживает отправку
    различных типов данных и файлов. Обычно метод POST исп-ся при
    отправке информации (например, заполненной формы логина) и загрузке
    данных на веб-сайт, таких как изображения и документы.

- *PUT* - исп-ся для создания (размещения) новых ресурсов на сервере.
    Если на сервере данный метод разрешен без надлежащего контроля, то
    это может привести к серьезным проблемам безоп-ти.

- *DELETE* - позволяет удалить существующие ресурсы на сервере.

- *HEAD* - данный метод при исп-и его в запросе позволит получить только
    заголовки, которые сервер бы вернул при получении GET-запроса.
    Запрос с исп-ем данного метода обычно производится для того, чтобы
    узнать размер запрашиваемого ресурса перед его загрузкой.

- *OPTIONS* - позволяет запросить информацию о сервере, в том числе
    информацию о допускаемых к исп-ю на сервере HTTP-методов.

- *PATCH* - позволяет внести частичные изменения в указанный ресурс по
    указанному расположению.
________________________________________________________________________

Коды состояний:

- 1xx - исключительно информативный характер и никак не влияют на
    обработку запроса.
- 2xx - возвращаются в случае успешной обработки клиентского запроса.
- 3xx - возвращаются, если серверу нужно перенаправить клиента.
- 4xx - означают, что на стороне клиента был отправлен некорректный
    запрос.
- 5xx - приходит, если на стороне сервера возникла ошибка.

Самые частые примеры:

- 200 OK - возвращается в случае успешной обработки запроса, при этом
    тело ответа обычно содержит запрошенный ресурс.
- 302 Found - перенаправляет клиента на другой URL. Например, данный код
    может прийти, если клиент успешно прошел процедуру аутентификации и
    теперь может перейти на страницу своей учетной записи.
- 400 Bad Request - запрос был сформирован с ошибками.
- 403 Forbidden - клиент не обладает достаточными правами доступа к
    запрошенному ресурсу. Также данный код можно встретить, если сервер
    обнаружил вредоносные данные, отправленные клиентом в запросе.
- 404 Not Found - можно увидеть, если запросить у сервера ресурс,
    которого не существует на сервере.
- 500 Internal Error - возвращается сервером, когда он не может по
    определенным причинам обработать запрос.
________________________________________________________________________

### <u> Прочие протоколы передачи данных </u> ###

- *SSH* (Secure Shell) - защищенный протокол, который исп-ся для
    подключения к серверам. Клиент-сервер.

- *FTP* (File Transfer Protocol) - протокол передачи файлов.
    Клиент-серверный протокол связи с 2 линиями - командной и
    транспортной. Поддерживает аутентификацию, но передает данные в
    открытом виде (для защищенной передачи исп-ся SFTP или FTPS). Исп-ет
    порты 20, 21.

- *BitTorrent* - пиринговый протокол связи. Пиринговый =
    децентрализованный, где все участники равны между собой. В случае
    данного протокола файл передается от всех участников соединения по
    частям, в т.ч. от тех, кто в данный момент данный файл скачивает.
    Обычно исп-ет порты 6881-6889 (TCP) для обмена данными и порт 6969
    для связи с трекером.

- *SMTP* (Simple Mail Transfer Protocol) - протокол передачи эл. почты.
    Функционирует по принципу "хранения и пересылки", где сообщения
    могут проходить через несколько промежуточных серверов. Расширения
    протокола включают аутентификацию (SMTP-AUTH) и шифрование
    (STARTTLS). Исп-ет порты 25, 587.
________________________________________________________________________

### <u> Другие прикладные протоколы </u> ###

- *DHCP* (Dynamic Host Configuration Protocol) - протокол динамического
    назначения IP-адресов и пар-ров сети клиентам для избежания ручной
    настройки.

- *Modbus* - самый распространенный промышленный протокол для
    M2M-взаимодействия. Подвиды:
    
    - *Modbus RTU* - данные кодируются в двоичный формат, а разделителем
        пакетов служит временной интервал. Этот протокол критичен к
        задержкам и не может работать, например, на модемных линиях. По
        интерфейсу RS-232.

    - *Modbus TCP* - структура пакетов схожа с Modbus RTU, данные также
        кодируются в двоичный формат, и упаковываются в обычный
        TCP-пакет, для передачи по IP-сетям. Проверка целостности,
        используемая в Modbus RTU, не применяется, так как TCP уже имеет
        собственный механизм контроля целостности. Порт: 502.
    
    Slave - получатель, master - отправитель. Только отправитель может
    инициализировать отправку и только он знает о состоянии подключения.
    Слейвов мб не более 247, адрес 0 используется для широковещательных
    запросов от мастера, у мастера адреса нет.

- *SNMP* (Simple Network Management Protocol) - стандартный протокол для
    мониторинга и управления сетевыми устройствами. Исп-ет порты 161,
    162.

- *POP3*, *IMAP* - для получения и управления эл. почтой соотв. Исп-ют
    порты 110 и 143 соотв.
________________________________________________________________________

## ПАКЕТЫ ПРОТОКОЛОВ ##

### <u> VPN </u> ###

*VPN* (Virtual Private Network) - виртуальная приватная сеть. Защищенный
тип соединения для удаленного доступа к приватным данным или для
создания тоннеля между серверами с приватными данными.

VPN-протокол состоит из туннелирования и шифрования. Протокол
туннелирования создает соединение между вашим уст-вом и VPN-сервером, а
протокол шифрования - шифрует данные, чтобы никто не смог перехватить
или подделать их.
________________________________________________________________________

Работает следующим образом:

- Поль-ль выбирает сервер в сервисе VPN и подключается к нему со своего
    уст-ва.

- VPN-сервис создает зашифрованный туннель между клиентом и сервером. В
    нем шифрует передаваемые данные с помощью протокола.

- VPN-сервер получает и расшифровывает трафик. Для этого он исп-ет
    специальные ключи шифрования.

- VPN-сервер заменяет информацию о поль-ле на свою и перенаправляет на
    целевой сайт клиентский запрос, с которым нужно установить
    соединение.

- VPN-сервер получает ответ, шифрует и перенаправляет его поль-лю. Для
    расшифровки данных VPN-клиент и сервер исп-ют специальные ключи
    шифрования.
________________________________________________________________________

Имеет ряд различных протоколов. Вот далеко не самый полный список:

- *PPTP* - один из первых, устарел.
- *SSTP* - нормальная скорость, есть уязвимости, требовательный.
- *IPsec* - защита соединения на уровне IP.
- *L2TP/IPsec* - устарел.
- *IPsec/IKEv2* - стабильный.
- *OpenVPN* - золотой стандарт, высокая скорость и безоп-ть.
- *WireGuard* - скорость.
- *Lightway* - баланс безоп-ти и скорости.
- *SoftEther* - многопротокольная VPN-система.
- *VLESS/VMess + XTLS-Reality* - протокол-невидимка.
- *Shadowsocks* - протокол-невидимка.
________________________________________________________________________

# API И СЕТИ #

## REST API ##

*REST* (Representational State Transfer) - это архитектурный подход,
который устанавливает ограничения для API.

REST-подход к архитектуре позволяет сделать сервисы отказоустойчивыми,
гибкими и производительными, а при их масштабировании и внесении
изменений не возникает больших сложностей.

Обычно принимает станд. HTTP-методы для взаимод-я и возвращает в
качестве ответа данные в формате JSON.
________________________________________________________________________

Требования к проектированию API для RESTful сервисов:

- Клиент-серверная модель (client-server model).
- Отсутствие состояния (statelessness).
- Кэширование (cacheability).
- Единообразие интерфейса (uniform interface).
- Многоуровневая система (layered system).
- Код по требованию (code on demand) - необязательно.

Рассмотрим их подробнее.
________________________________________________________________________

*Клиент-серверная модель* - подразумевает разделение двух
взаимодействующих систем на клиент (программа, которая делает запрос) и
сервер (программа, которая принимает, обрабатывает и отвечает на
запрос).

Цель: разделение обязанностей, что позволяет разрабатывать сервер
отдельно от каждой возможной реализации клиента.
________________________________________________________________________

*Отсутствие состояния* - на сервере не хранится никаких данных о прошлых
взаимод-ях с клиентом, а каждый запрос должен содержать всю информацию
для его обработки.

Цель: снизить нагрузку на сервер; убрать зав-ть м/ запросами для того,
чтобы при проблемах с к-л запросом не ломать логику взаимод-я.
________________________________________________________________________

*Кэширование* - сохранение результатов запросов у клиента или
промежуточных серверов.

Цель: снизить нагрузку на сервер (вместо обработки одного и того же
запроса несколько раз подружать данные из кэша).

В данном требовании важно грамотно учесть баланс и не кэшировать всю
информацию - это как затратно по памяти, так и некоторая информация со
временем устаревает. Тут уместным будет решить наподобие LRU-кэша для
хранения только часто запрашиваемой информации, чтобы избежать проблемы
с памятью, и не кэшировать что-то часто изменяющееся (или реализовывать
обновление по требованию) для решения проблемы с устареванием. Кроме
того, ответ от RESTful сервера подразумевает наличие в себе информации о
том, можно ли данную информацию кэшировать.
________________________________________________________________________

*Единообразие интерфейса* - должен быть единый способ обращения к
каждому ресурсу в сервисе. Для реализации единообразного интерфейса в
REST API используется принцип HATEOAS (Hypermedia as the Engine of
Application State).

Цель: предсказуемость и понятность взаимодействия с каждым подсервисом
для разработчиков клиента и других подсервисов и (или) для поль-ля.
________________________________________________________________________

*Многоуровневая система* - наличие прокси-серверов для к-л конкретных
задач перед переходом непосредственно к основному серверу. В данных
прокси-серверах может происходить кэширование, проверка безопасности,
предварительная или доп. обработка данных, балансировка в случае наличия
нескольких основных серверов и т.д.

Цель: снизить нагрузку на сервер, обеспечить выполнение важных ф-ций
перед попаданием запроса (или его производной) на основной сервер.

При этом каждый участник цепи не знает ничего о пути перемещения
запроса и всех его участниках, кроме предыдущего и следующего. Кроме
того, нет и знания у любого участника, кому по роли он отправляет запрос
\- прокси или основному серверу, - как и не знает, кому отправляет ответ
\- клиенту или прокси.

Такой подход позволяет без особых проблем добавить в цепочку участника
или убрать, а также изолировать основной сервер от информации, которую
ему не надо обрабатывать (вредоносной или закэшированной на прокси,
например), добавить доп. обработку, создать микросервисную архитектуру с
возможными разветвлениями и избавить от лишней нагрузки основной сервер.
________________________________________________________________________

*Код по требованию* - сервер в ответ на запрос может отправить исходный
код, который выполняется уже на стороне клиента. Благодаря этому можно
передавать целые сценарии.

В REST API требование необязательно, потому что не всем сайтам и
сервисам нужно умение работать с готовыми скриптами.
________________________________________________________________________

Т.к. REST - архитектурный подход, а не протокол, в нем не заложено
никаких конкретных методов. Но чаще всего его применяют вместе со
стандартом HTTP, в котором заложены собственные методы (CRUD).

REST API исп-ся, когда:

- Пропускная способность соединения с сервером ограничена.
- Нужно соединить мобильные приложения с серверными.
- Проект разбит на микросервисы.
- Сервис предоставляет свои возм-ти другим разработчикам.
- Исп-ся AJAX (Asynchronous Javascript and XML).
- Известно, что систему нужно будет масштабировать.
________________________________________________________________________

## gRPC API ##

*gRPC* - это высокопроизводительная платформа с открытым исходным кодом
от Google. Он использует протокол HTTP/2 для передачи данных и Protocol
Buffers (protobuf) в качестве языка определения интерфейса.

gRPC поддерживает четыре типа взаимод-я: унарный (стандартный
запрос-ответ), потоковая передача данных с сервера, потоковая передача
данных от клиента и двунаправленная потоковая передача.

Основные преимущества gRPC - эффективность за счет исп-я HTTP/2 и
protobuf, а также гибкость за счет различных типов взаимод-я. За счет
этих преимуществ является отличным решением для микросервисов и систем,
требующих высокой производительности.
________________________________________________________________________

Protocol Buffers - язык описания интерфейсов и система сериализации от
Google. protobuf позволяет определять структуру данных и интерфейсы
сервисов в специальных файлах .proto. Эти файлы компактны, эффективны и
позволяют автоматически генерировать исходный код для различных ЯП.

protobuf сериализует структурированные данные в меньший объем по
сравнению с такими форматами, как JSON или XML. Это уменьшает размеры
пакетов данных, ускоряя их передачу и обработку.

gRPC работает на основе определения сервисов и их методов в файлах
.proto. Определяются структуры данных (сообщения) и сервисы с методами,
которые принимают и возвращают эти сообщения.

Исп-ся файлы .proto для описания сервисов и методов, которые мб вызваны
удаленно. Каждый метод сервиса может принимать один тип запроса и
возвращать один тип ответа. Используя инструменты gRPC, из этих .proto
файлов генерируется код на целевом ЯП. Этот код включает в себя
клиентские и серверные стабы, которые разработчики исп-ют для реализации
логики приложения.
________________________________________________________________________

## ПРОЧИЕ API ##

- *SOAP* (Simple Object Access Protocol) - это протокол для обмена
    структурированной информацией в веб-сервисах с исп-ем XML. Он
    обладает высокой расширяемостью и позволяет осуществлять обмен
    данными ч/ несколько различных транспортных протоколов, включая
    HTTP, SMTP и др.
    
    API SOAP известны своей надежностью и часто используются в
    энтерпрайз-разработке. Они предлагают встроенную обработку ошибок и
    их можно использовать с различными сетевыми протоколами. Однако
    зав-ть SOAP от XML может приводить к большим объемам передаваемых
    данных, что делает его менее эффективным по сравнению с др. API в
    каких-то сценариях исп-я.

- *WebSocket* - обеспечивает постоянный, полнодуплексный канал связи м/
    клиентом и сервером. В отличие от REST и SOAP, которые исп-ют формат
    "запрос-ответ", WebSocket сохраняет соединение открытым, что
    позволяет передавать данные в режиме реального времени. Это делает
    WebSocket API идеальным для приложений, требующих функциональности в
    реальном времени.
    
    Несмотря на свою мощь, WebSocket API могут быть более сложными в
    реализации и требуют больше ресурсов для поддержания открытых
    соединений.

- *GraphQL* -  представляет собой язык запросов к API и рабочую среду
    для выполнения этих запросов. В отличие от REST API, где вам нужно
    делать запросы к различным эндпоинтам, чтобы получить соотв. данные,
    GraphQL позволяет сделать один запрос, чтобы получить именно те
    данные, которые вам нужны.
    
    В GraphQL пользователи определяют форму и размер ответа, что
    приводит к более эффективной загрузке данных и уменьшению избыточной
    выборки данных. Он отлично подходит для сложных систем и
    микросервисов, где данные распределены м/ различными сервисами.
