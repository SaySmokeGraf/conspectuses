# КРАТКАЯ ТЕОРИЯ #

*Django* - это фреймворк для создания веб-приложений с помощью ЯП
Python. Бесплатный, open source проект. Django по умолчанию предлагает
готовую функциональность для ряда распространенных задач, например,
систему аутентификации, генерацию карт сайта и т.д. В Django большое
внимание уделяется безопасности, благодаря чему фреймворк помогает
разработчикам избежать многих распространенных проблем в системе
безопасности, например, SQL-инъекций.
________________________________________________________________________

Django реализует архитектурный паттерн Model-View-Template (MVT),
который по факту является модификацией распростаненного в
веб-программировании паттерна Model-View-Controller (MVC).

Схематично MVT представляется как:

```
+---------+    +----------------+    +------+    +-------+    +----+
|         | -> | URL dispatcher | -> |      | -> |       | -> |    |
|         |    +----------------+    |      |    |       |    |    |
| Browser |                          | View |    | Model |    | DB |
|         |    +----------------+    |      |    |       |    |    |
|         | <- |    Template    | <- |      | <- |       | <- |    |
+---------+    +----------------+    +------+    +-------+    +----+
```

Здесь:

- *URL dispatcher* (URL диспетчер) - эл-т, который при получении запроса
    на основании запрошенного адреса URL определяет, какой ресурс должен
    обрабатывать данный запрос.

- *View* (представление) - получает запрос, обрабатывает его и
    отправляет в ответ поль-лю некоторый ответ. Если для обработки
    запроса необходимо обращение к модели и БД, то View взаимод-ет с
    ними. Для создания ответа может применять Template или шаблоны. В
    архитектуре MVC этому компоненту соотв-ют контроллеры (но не
    представления).

- *Model* (модель) - описывает данные, используемые в приложении.
    Отдельные классы, как правило, соотв-ют таблицам в БД.

- *Template* (шаблон) - представляет логику представления в виде
    сгенерированной разметки HTML. В MVC этому компоненту соотв-ет View,
    т.е. представления.
________________________________________________________________________

*Django REST framework* - это мощный и гибкий набор инструментов для
создания Web API на основе фреймворка Django.

## ПЕРВЫЕ ШАГИ ##

`pip install Django` - для установки последней версии фреймворка.
________________________________________________________________________

`django-admin` - утилита для администрирования проекта.

Имеет команды:

- `django-admin startproject <name>` - создать проект name.
________________________________________________________________________

После создания проекта в корне появится каталог с именем проекта, а
также несколько файлов:

- `manage.py` - выполняет различные команды проекта, например, создает и
    запускает приложение.

- `<name>` - собственно папка проекта name, которая содержит следующие
    файлы:

    - `__init__.py` - для рассматривания папки как пакета.
    - `settings.py` - содержит настройки конфигурации проекта.
    - `urls.py` - содержит шаблоны URL-адресов, по сути определяет
        систему маршрутизации проекта.
    - `wsgi.py` - содержит свойства конфигурации WSGI (Web Server
        Gateway Inerface). Он используется при развертывании проекта.
    - `asgi.py` - название файла представляет сокращение от Asynchronous
        Server Gateway Interface и расширяет возможности WSGI, добавляя
        поддержку для взаимодействия между асинхронными веб-серверами и
        приложениями.

`python manage.py runserver` - для запуска сервера. По умолчанию
запускается по адресу "http://127.0.0.1:8000/".
________________________________________________________________________

Веб-приложение или проект Django состоит из отдельных приложений. Вместе
они образуют полноценное веб-приложение. Каждое приложение представляет
какую-то определенную функциональность или группу функциональностей.
Один проект может включать мн-во приложений. Это позволяет выделить
группу задач в отдельный модуль и разрабатывать их относительно
независимо от других. Кроме того, мы можем переносить приложение из
одного проекта в другой независимо от другой функциональности проекта.

При создании проекта он уже содержит несколько приложений по умолчанию:

- `django.contrib.admin`
- `django.contrib.auth`
- `django.contrib.contenttypes`
- `django.contrib.sessions`
- `django.contrib.messages`
- `django.contrib.staticfiles`

В settings.py в переменной `INSTALLED_APPS` перечислены все
установленные в проекте приложения.
________________________________________________________________________

`python manage.py startapp name` - для создания в проекте своего
приложения name. После этого в проекте появится папка со всеми файлами
нового приложения.

А именно:

- `migrations` - предназначена для хранения миграций - скриптов, которые
    позволяют синхронизировать структуру БД с определением моделей.

- `__init__.py` - для рассматривания папки как пакета.

- `admin.py` - предназначен для административных ф-ций, в частности,
    здесь призводится регистрация моделей, которые исп-ся в интерфейсе
    администратора.

- `apps.py` - определяет конфигурацию приложения.

- `models.py` - хранит определение моделей, которые описывают
    используемые в приложении данные.

- `tests.py` - хранит тесты приложения.

- `views.py` - определяет ф-ции, которые получают запросы поль-лей,
    обрабатывают их и возвращают ответ.

После этого для того, чтобы приложение работало, надо добавить его по
имени как строке в переменную INSTALLED_APPS.
________________________________________________________________________

Hello World на Django:

1. Создаем приложение hello.

2. В hello/views.py прописываем следующее:

    ```py
    from django.http import HttpResponse
    
    def index(request):
        return HttpResponse('Hello World')
    ```

    Этот код создает функцию-обработчик эндпоинта, которая возвращает
    HTTP-ответ с "Hello World".

3. В urls.py прописываем:

    ```py
    from django.urls import path
    from hello import views
    
    urlpatterns = [
        path('', views.index, name='home'),
    ]
    ```

    Данная запись связывает эндпоинт по URL корня с ф-цией-обработчиком
    из hello/views.py. Дополнительно задается имя данному маршруту -
    "home".

## ЗАПРОСЫ И ОТВЕТЫ ##

### Представления ###

За обработку запросов отвечают ф-ции-обработчики, называемые
*представлениями* (*views*) и описываемые в файлах `views.py` каждого из
приложений. Они принимают обязательный первый параметр - параметры
запроса в виде экземпляра класса `django.http.HttpRequest` и возвращают
результат, который отправляется поль-лю.

Ответ может возвращаться по-разному, основной из них -
`django.http.HttpResponse`. Он принимает строку (которая мб
HTML-разметкой) и возвращает ее поль-лю.

Чтобы эти ф-ции сопоставлялись с URL, надо для низ обозначить маршруты в
`urls.py`.

Пример:

```py
# app_name/views.py
...

def index(request):  # request имеет ТД HttpRequest
    return HttpResponse("Главная")
 
def about(request):
    return HttpResponse("О сайте")
...


# urls.py

from django.urls import path
from app_name import views
 
urlpatterns = [
    path('', views.index),  # эндпоинт корня ('/')
    path('about', views.about),  # эндпоинт '/about'
    ...
]
```

### Маршрутизация ###

Маршруты нужны для сопоставления эндпоинта и ф-ции, его обрабатывающей
(представления). Маршрутизация производится в файле urls.py с помощью
специальной переменной `urlpatterns` и ф-ций `django.urls.path` или
`django.urls.re_path`.

Переменная urlpatterns отвечает за список маршрутов. Каждый маршрут
задается ф-цией path или re_path. Первая задает маршрут по четкому URL с
возм-тью указать параметры запроса, а вторая задает URL ч/ регулярное
выражение.

Сигнатуры:

- `path(route, view, kwargs=None, name=None)` - сопоставляет эндпоинт
    route и представление view. При этом name позволяет задать имя
    маршруту, а kwargs - аргументы по ключу для передачи в
    ф-цию-представление.

- `re_path(route, view, kwargs=None, name=None)` - то же, но route
    задается как регулярное выражение (`r'...'`).
________________________________________________________________________

Пример 1:

```py
from django.urls import path
from hello import views
 
urlpatterns = [
    path('', views.index),
    path('about', views.about),
    path('contact', views.contact),
]
```

Тут исп-ся path, и т.о. есть эндпоинты '/', '/about', '/contact', и хотя
засчет четкого указания это быстрее re_path, при этом нет даже
эндпоинтов '/about/' и '/contact/'.

Пример 2:

```py
from django.urls import path, re_path
from hello import views
 
urlpatterns = [
    path('', views.index),
    re_path(r'^about', views.about),
    re_path(r'^contact', views.contact),
]
```

Тут исп-ся re_path, который принимает регулярные выражения, и теперь
есть мн-во возможных URL, обрабатываемых данными маршрутами. С одной
стороны, добавляет удобства (есть и '/about', и '/about/'). С другой,
регулярные выражения медленнее, а в общий пул в данном случае попадают и
не самые ожидаемые URL. Сюда относятся, например, '/about' + что угодно.
Т.о. это может быть околесица ('/aboutaboutaboutsomebadwords12345123')
или очень длинная строка, которая при DoS-атаках будет забивать память,
ожидая обработки, а не отбрасываться на этапе сверки.
________________________________________________________________________

Важно правильно выстраивать очередность объявления маршрутов. При исп-ии
re_path более конкретные маршруты надо объявлять раньше
('/about/contacts' раньше '/about'). Это связано с тем, что Django
поочередно проверяет маршруты, и в обратном от правильного случая он
первее наткнется на менее конкретный маршрут вне зав-ти от входных
данных и обработает оба варианта одним обработчиком.

Наглядно:

```py
# неправильно
urlpatterns = [
    re_path(r'^about', views.about),
    re_path(r'^about/contact', views.contact),
]
# '/about' и '/about/contact' оба подходят под r'^about', который стоит
# раньше => отработает на оба случая views.about, а views.contact
# никогда не будт вызван

# правильно
urlpatterns = [
    re_path(r'^about/contact', views.contact),
    re_path(r'^about', views.about),
]
# при проверке '/about/contact' Django наткнется первее на более
# конкретный маршрут => отработает через views.contact, а при проверке
# '/about' r'^about/contact' не подойдет, подойдет r'^about' =>
# обработается ч/ views.about
```
________________________________________________________________________

При задании маршрута ч/ path или re_path можно передать в него пар-ры ч/
kwargs по классике синтаксиса Python в виде словаря, но такая явная
передача доп. пар-ров - тема более специфичная.
________________________________________________________________________

Можно делать вложенные маршруты с помощью `django.urls.include`.

Пример:

```py
from django.urls import path, include
from hello import views
  
product_patterns = [  # будущие вложенные маршруты
    path("", views.products),
    path("new", views.new),
    path("top", views.top),
]
 
urlpatterns = [
    path("", views.index),
    path("products/", include(product_patterns)),  # вкладываем
]

# получаем эндпоинты
# /
# /products/
# /products/new
# /products/top
```

### Данные запроса (HttpRequest) ###

Любые данные запроса передаются в представление в виде первого
обязательного пар-ра экземпляра HttpRequest. В нем хранятся все данные
запроса по следующим атрибутам:

- `scheme` - схема запроса (HTTP или HTTPS).
- `body` - представляет тело запроса в виде строки байтов.
- `path` - представляет путь запроса.
- `method` - метод запроса (GET, POST, PUT и т.д.).
- `encoding` - кодировка.
- `content_type` - тип содержимого запроса (значение заголовка
    CONTENT_TYPE).
- `GET` - объект в виде словаря, который содержит параметры запроса GET.
- `POST` - объект в виде словаря, который содержит параметры запроса
    POST.
- `COOKIES` - отправленные клиентом куки.
- `FILES` - отправленные клиентом файлы.
- `META` - хранит все доступные заголовки HTTP в виде словаря. Набор
    заголовков зависит от клиента и сервера, некоторые из них:
    - `CONTENT_LENGTH` - длина содержимого.
    - `CONTENT_TYPE` - MIME-тип запроса.
    - `HTTP_ACCEPT` - типы ответа, которые принимает клиент.
    - `HTTP_ACCEPT_ENCODING` - кодировка, в которой клиент принимает
        ответ.
    - `HTTP_ACCEPT_LANGUAGE` - язык ответа, который принимает клиент.
    - `HTTP_HOST` - хост сервера.
    - `HTTP_REFERER` - страница, с которой клиент отправил запрос (при
        ее наличии).
    - `HTTP_USER_AGENT` - юзер-агент или информация о браузере клиента.
    - `QUERY_STRING` - строка запроса.
    - `REMOTE_ADDR` - IP-адрес клиента.
    - `REMOTE_HOST` - имя хоста клиента.
    - `REMOTE_USER` - аутентификационные данные клиента (при наличии).
    - `REQUEST_METHOD` - тип запроса (GET, POST).
    - `SERVER_NAME` - имя хоста сервера.
    - `SERVER_PORT` - порт сервера.
    - `headers` - заголовки запроса в виде словаря

Также HttpRequest определяет ряд методов:

- `get_full_path()` - возвращает полный путь запроса, включая строку
    запроса.
- `get_host()` - возвращает хост клиента, для этого исп-ся значения
    заголовков HTTP_X_FORWARDED_HOST (если включена опция
    USE_X_FORWARDED_HOST) и HTTP_HOST.
- `get_port()` - возвращает номер порта.

### Ответы ###

В большинстве простых случаев решается через HttpResponse. Сигнатура:

```py
HttpResponse(
    content=b'',
    content_type=None,
    status=200,
    reason=None,
    charset=None,
    headers=None
)
```

Параметры:

- `content` - содержимое ответа в виде строки байтов. Если передается
    другое содержимое, то оно конвертируется в строку байтов.
- `content_type` - MIME-тип ответа, устанавливает HTTP-заголовок
    Content-Type. Если этот пар-р не установлен, то применяется mime-тип
    text/html и значение настройки DEFAULT_CHARSET, т.е. в итоге будет:
    "text/html; charset=utf-8".
- `charset` - кодировка ответа в виде строки. По умолчанию Django
    пытается установить кодировку из пар-ра content_type, а в случае
    неудачи для установки кодировки применяется настройка
    DEFAULT_CHARSET.
- `status` - статусный код ответа. По умолчанию равно 200.
- `reason_phrase` - сообщение, которое отправляется в вместе статусным
    кодом.
- `headers` - заголовки ответа в виде словаря.

Атрибуты:

- `content` - содержимое ответа в виде строки байтов.
- `headers` - отправляемые заголовки в виде словаря.
- `charset` - кодировка ответа в виде строки. По умолчанию Django
    пытается установить кодировку из заголовка content_type, а в случае
    неудачи для установки кодировки применяется настройка
    DEFAULT_CHARSET.
- `status_code` - статусный код ответа.
- `reason_phrase` - сообщение, которое отправляется в вместе статусным
    кодом.
________________________________________________________________________

Для перенаправления исп-ся классы `HttpResponseRedirect` для временного
перенаправления (302) и класс `HttpResponsePermanentRedirect` для
постоянного перенаправления (307).

Пример:

```py
def contact(request):
    return HttpResponseRedirect("/about")
 
def details(request):
    return HttpResponsePermanentRedirect("/")
```

Кроме того, для конкретных статус-кодов и формирования ответов под
спецификации исп-ся:

- `HttpResponseNotModified` - 304 (Not Modified).
- `HttpResponseBadRequest` - 400 (Bad Request).
- `HttpResponseForbidden` - 403 (Forbidden).
- `HttpResponseNotFound` - 404 (Not Found).
- `HttpResponseNotAllowed` - 405 (Method Not Allowed).
- `HttpResponseGone` - 410 (Gone).
- `HttpResponseServerError` - 500 (Internal Server Error).

В функцию конструктора этих классов можно передать некоторые данные,
например, сообщение об ошибке.

Пример:

```py
# views.py
from django.http import HttpResponse, HttpResponseNotFound, HttpResponseForbidden, HttpResponseBadRequest
 
 
def index(request, id):
    people = ["Tom", "Bob", "Sam"]
    # если пользователь найден, возвращаем его
    if id in range(0, len(people)):
        return HttpResponse(people[id])
    # если нет, то возвращаем ошибку 404
    else:
        return HttpResponseNotFound("Not Found")
 
def access(request, age):
    # если возраст НЕ входит в диапазон 1-110, посылаем ошибку 400
    if age not in range(1, 111):
        return HttpResponseBadRequest("Некорректные данные")
    # если возраст больше 17, то доступ разрешен
    if(age > 17):
        return HttpResponse("Доступ разрешен")
    # если нет, то возвращаем ошибку 403
    else:
        return HttpResponseForbidden("Доступ заблокирован: недостаточно лет")
```

За ответ в формате JSON отвечает `JsonResponse`. Сигнатура:

```py
JsonResponse(
    data,
    encoder=DjangoJSONEncoder,
    safe=True,
    json_dumps_params=None,
    **kwargs
)
```

Пар-ры:

- `data` - отправляемые данные.
- `encoder` - сериализатор, которые сериализует отправляемые данные в
    формат JSON. По умолчанию представляет тип
    `django.core.serializers.json.DjangoJSONEncoder`.
- `safe` - флаг безопасной сериализации. Если равно False, то
    сериализации подлежит любой объект. Если же равно True, то
    отправляемые данные должны представлять тип dict. По умолчанию равно
    True.
- `json_dumps_params` - словарь аргументов, который передается в ф-цию
    json.dumps() для генерации ответа.

Для сериализации своего ТД нужно исп-ть свои сериализаторы.

Пример:

```py
from django.http import JsonResponse
from django.core.serializers.json import DjangoJSONEncoder

 
class Person:
    def __init__(self, name, age):
        self.name = name      # имя человека
        self.age = age        # возраст человека
 
class PersonEncoder(DjangoJSONEncoder):
    def default(self, obj):
        if isinstance(obj, Person):
            return {"name": obj.name, "age": obj.age}
            # return obj.__dict__
        return super().default(obj)

def index(request):
    bob = Person("Bob", 41)
    return JsonResponse(bob, safe=False, encoder=PersonEncoder)
```

Сериализатор наследуется от DjangoJSONEncoder и переобозначает метод
`default`, после чего пар-ру encoder экземпляра JsonResponse
присваивается класс этого сериализатора.

### Path-параметры ###

*Path-пар-ры* - передаются в URL. В Django задаются при маршрутизации и
автоматически передаются как kwargs в представление.

Пример:

```py
urlpatterns = [
    path("", views.index),
    path("user/<str:name>", views.user),
]
```

Т.е. задается ч/ URL с синтаксисом `<спецификатор:имя-параметра>`.
Поддерживаются следующие спецификаторы:

- `str` - строка за исключенем символа "/". Если спецификатор не указан,
    то исп-ся по умолчанию.
- `int` - положительное число.
- `slug` - пос-ть буквенных символов ASCII, цифр, дефиса и символа
    подчеркивания (например, "building-your-1st-django-site").
- `uuid` - идентификатор UUID (например,
    "075194d3-6885-417e-a8a8-6c931e272f00").
- `path` - строка, которая также может включать символ "/", в отличие от
    спецификатора str.

Можно задавать сразу несколько path-пар-ров (например,
`"user/<str:name>/<int:age>"`).

Можно комбинировать со вложенностью маршрутов как в списке с вложенными
маршрутами, так и в строке с include.
________________________________________________________________________

Можно задать значения пар-ров по умолчанию ч/ значения по умолчанию
пар-ров ф-ции согласно синтаксису Python для представлений и задание
различных маршрутов. Это создает возможность не задавать явно значения
пар-ров или делать их необязательными к указанию.

Например:

```py
# views.py
...

def user(request, name="Undefined", age =0):
    return HttpResponse(f"<h2>Имя: {name}  Возраст: {age}</h2>")

...

# urls.py
...

urlpatterns = [
    path("", views.index),
    path("user", views.user),
    path("user/<name>", views.user),
    path("user/<name>/<int:age>", views.user),
]

...
```

В данном случае объявление идет от URL с меньшим указанием пар-ров до
URL с большим.
________________________________________________________________________

Можно делать и ч/ re_path:

```py
# views.py
...

def user(request, name="Undefined", age =0):
    return HttpResponse(f"<h2>Имя: {name}  Возраст: {age}</h2>")
...

# urls.py
...

urlpatterns = [
    path("", views.index),
    re_path(r"^user/(?P<name>\D+)/(?P<age>\d+)", views.user),
    re_path(r"^user/(?P<name>\D+)", views.user),
    re_path(r"^user", views.user),
]

...
```

Синтаксис вида `(?P<имя-параметра>регулярка)`.

В данном случае указание нескольких URL для учета необязательных пар-ров
идет по тому же принципу, что и при указании менее или более конкретных
маршрутов для re_path - сначала более конкретные, а затем - менее.
________________________________________________________________________

### Query-параметры ###

*Query-пар-ры* - пар-ры, которые также передаются в URL, но после
символа "?" в конце адреса.

Например: `http://127.0.0.1:8000/index?id=3&name=Tom`.

Для их чтения исп-ся атрибуты класса HttpRequest (см. "Данные запроса
(HttpRequest)") в views.py.

Продолжая пример:

```py
def user(request):
    age = request.GET.get("age")
    name = request.GET.get("name")
    return HttpResponse(f"<h2>Имя: {name}  Возраст: {age}</h2>")
```

Для необязательных пар-ров надо указать значения по умолчанию:

```py
def user(request):
    age = request.GET.get("age", 0)
    name = request.GET.get("name", "Undefined")
    return HttpResponse(f"<h2>Имя: {name}  Возраст: {age}</h2>")
```

### Cookie-параметры ###

Куки исп-ся для хранения данных поль-ля в браузере и отправки их на
сервер, ограничены 4096 байтами. Куки можно как отправлять с сервера на
клиент, так и получать сервером от клиента.
________________________________________________________________________

За установку куки и отправку их клиенту отвечают метод `set_cookie` и
`set_signed_cookie` класса HttpResponse. Сигнатура:

```py
set_signed_cookie(
    key,
    value='',
    salt='',
    max_age=None,
    expires=None,
    path='/',
    domain=None,
    secure=False,
    httponly=False,
    samesite=None
)
```

У set_cookie нет пар-ра salt. Отличаются методы тем, что куки ч/
set_cookie не зашифрован, а ч/ set_signed_cookie - зашифрован с помощью
соли в пар-ре salt.

Пар-ры:

- `key` - ключ или имя куки.
- `value` - значение куки.
- `salt` - соль шифрования.
- `max_age` - макс. время жизни куки в секундах. Это мб либо объект
    timedelta, либо число, либо значение None (ограничивает время жизни
    куки текущей сессией браузера, является значением по умолчанию).
- `expires` - время и дата, когда истекает действие куки. Должен
    представлять строку в формате "Wdy, DD-Mon-YY HH:MM:SS GMT" или
    объект datetime.datetime.
- `path` - путь, для которого устанавливаются куки.
- `domain` - домен, к которому применяются куки.
- `secure` - устанавливает используемый протокол. Так, если имеет
    значение True, то куки будут посылаться на сервер только в запросе
    по протоколу HTTPS.
- `httponly` - устанавлиет доступность для скриптов javascript на
    клиенте. Так, значение `httponly=True` предотвращает доступ к куки
    из кода javascript на клиенте.
- `samesite` - устанавливает разрешения на отправку куки в кроссдоменных
    запросах. Так, значения `samesite='Strict'` и `samesite='Lax'`
    указывают браузеру не посылать куки в кроссдоменных запросах.
    Значение по умолчанию `samesite='None'` разрешает отправку куки в
    кроссдоменных запросах.

Пример:

```py
# views.py
from django.http import HttpResponse
 
# установка куки
def set(request):
    # получаем из строки запроса имя пользователя
    username = request.GET.get("username", "Undefined")
    # создаем объект ответа
    response = HttpResponse(f"Hello {username}")
    # передаем его в куки
    response.set_cookie("username", username)
    return response
```
________________________________________________________________________

Для получения куки у объекта HttpRequest можно использовать атрибут
`COOKIES`, который представляет словарь. Для получения зашифрованного
куки исп-ся метод `get_signed_cookie` класса HttpRequest. Сигнатура:

```py
get_signed_cookie(key, default=RAISE_ERROR, salt='', max_age=None)
```

Пар-ры:

- `key` - ключ куки, которые надо получить.
- `default` - значение по умолчанию, если куки с указанным ключом
    отсутствуют в запросе.
- `max_age` - макс. время жизни куки в секундах.
- `salt` - соль шифрования, должен иметь то же самое значение, которое
    передавалось в set_signed_cookie.

Продолжая пример выше:

```py
# views.py
from django.http import HttpResponse
 
# установка куки
def set(request):
    # получаем из строки запроса имя пользователя
    username = request.GET.get("username", "Undefined")
    response = HttpResponse(f"Hello {username}")
    # передаем его в куки
    response.set_cookie("username", username)
    return response
 
# получение куки
def get(request):
    # получаем куки с ключом username
    username = request.COOKIES["username"]
    return HttpResponse(f"Hello {username}")
```
