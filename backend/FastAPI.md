# ОСНОВНЫЕ ФУНКЦИИ #

## ПЕРВЫЕ ШАГИ ##

`fastapi` - модуль. Установка как стандартный пакет:
`pip install fastapi[standart]`. Содержит мн-во различных необх. для
правильной и удобной работы с FastAPI наподобие Pydantic (см. исп-е в
др. разделах данного конспекта).

`fasapi dev filename.py` - команда для терминала для запуска сервиса на
FastAPI в режиме разработчика. Для запуска в режиме продукта - убрать
`dev` в команде. В условиях расположения на локальной машине доступ
будет в браузере по адресу, который выведется в консоль (т.е. скорее
всего `127.0.0.1:8000`).

В случае наличия исключений и ошибок в таком формате запуска приложение
не крашится, а возвращает описание ошибки как полноценный HTTP-ответ в
JSON формате.
________________________________________________________________________

`app = FastAPI()` - создание приложения FastAPI.
________________________________________________________________________

*Эндпоинт* - путь после домена. По ним разделяются различные ресурсы,
операции, задачи и проч. Коренной эндпоинт - `/`, пример другого
эндпоинта: `/some/path/to/endpoint`.

Поддерживаются все HTTP-запросы: основные - POST, GET, PUT, DELETE, - и
более экзотические - OPTIONS, HEAD, PATCH, TRACE. Для каждого эндпоинта
возможна регистрация нескольких HTTP-методов.

Регистрация операции для эндпоинта (или просто регистрация эндпоинта) в
приложении FastAPI на примере GET-запроса (здесь и далее "app" -
экземпляр класса fastapi.FastAPI):

```py
@app.get('/some/path/to/endpoint')
async def some_func():
    ...  # ф-ция для обработки сервером GET-запроса к эндпоинту
    return ...
```

Как видно из примера, регистрация производится с помощью декоратора
`<имя-приложения>.<HTTP-метод>('<эндпоинт>')`. Ф-ция, оборачиваемая в
декоратор, представляет собой операцию, выполнямую по данному
HTTP-запросу. Т.к. FastAPI - асинхронный фреймворк, то и ф-ции исп-ся
обычно асинхронные, и важно поддерживать ее правильную работу. Тем не
менее, чисто технически возможно исп-е и обычных ф-ций, но с потерей
практически всех плюсов асинхронного устр-ва FastAPI.

Кроме того, довольно логино, что ф-ции следует возвращать что-то на
приходящий запрос, и ее ответ возвращается в `return`, как и в обычных
ф-циях. Поддерживаются все обычные типы данных Python, HTML-страницы,
ORM-объекты и модели Pydantic. Они автоматически преобразуются в JSON по
необх-ти для отправки как HTTP-ответа.
________________________________________________________________________

Т.о. Hello World в FastAPI:

```py
from fastapi import FastAPI

app = FastAPI()


@app.get('/')
async def helloworld():
    return {'message': 'Hello World'}
```
________________________________________________________________________

Крайне полезная вещь в разработке - автоматическая документация. Она
доступна по эндпоинту `/docs`. Там можно также опробовать
зарегистрированные эндпоинты.

Кроме того, по адресу `/openapi.json` достуна полная схема сервиса в
формате JSON.

## ПАРАМЕТРЫ ЗАПРОСА ##

### ТИПЫ ДАННЫХ ###

В первую очередь, с FastAPI и его автоматической валидацией работают все
простые типы данных Python есть ряд ТД.

- *int*, *float* - как обычно.

- *str* - как обычно. Кроме того, можно исп-ть унаследованные от него ТД
    из Pydantic наподобие `HttpUrl` для HTTP-адресов.

- *bool* - тоже как обычно, но в запросе в качестве True принимаются
    значения: 1, True, true, on, yes и их вариации написания. Иное
    значение - False.

- *list[\<type>]* - для body-пар-ров можно указывать вчистую, как
    обычно, в то время как для query-пар-ров лучше внутри
    typing.Annotated (см. соотв. блок в подтеме "Query-параметры").
    Тогда может принимать несколько переданных значений и сложить их в
    один список.
    
    Пример:

    ```py
    @app.get('/')
    async def get_root(q: Annotated[list | None, Query()] = None):
        return {'q': q}
    ```

    Тут сработает запрос вида "127.0.0.1:8000/?q=aaa&q=bbb", возвращая
    "{'q': ['aaa', 'bbb']}". Для валидации ТД в списке - указать тип.

- *dict[\<key_type>, \<val_type>]* - для body-пар-ров. Исп-ся, когда
    хочется получить неизвестные ключи либо когда хочется иметь ключи
    иного от str ТД. В таком случае в передаваемом JSON-представлении
    тела запроса будет, конечно, ТД str, но FastAPI при получении
    автоматически валидирует и преобразует данные.
________________________________________________________________________

В качестве ТД мб использованы *классы, дочерние классу `enum.Enum`*, с
перечислением возможных значений. Так можно ограничить возможные
значения до списка разрешенных, а также пользоваться Enum-дочерним
классом при обработке запроса с проверкой `is` или получая значение ч/
атрибут `value`.

Например:

```py
from enum import Enum

...

class SiteTheme(str, Enum):
    dark = 'dark'
    light = 'light'
    festive = 'festive'

...

@app.get('/')
async def root(theme: SiteTheme):
    msg = f'Hi!'
    if theme is SiteTheme.festive:
        msg = f'{msg} Happy Holidays!'
    return {'message': f'{msg} Theme now: {theme.value}.',
            'theme': theme}
```

Как видно, в ответе можно исп-ть без атрибута value, если передавать
непосредственно theme, т.к. FastAPI сам преобразует theme в его значение
str согласно SiteTheme для передачи в стандарте JSON.

Примеры запросов:

- `127.0.0.1:8000/?theme=dark` - работает, ответ:
    `{'message': 'Hi! Theme now: dark.', 'theme': 'dark'}`.
- `127.0.0.1:8000/?theme=midnight-blue` - ошибка.
- `127.0.0.1:8000/?theme=festive` - работает, ответ:
    `{'message': 'Hi! Happy Holidays! Theme now: festive.', 'theme': 'festive'}`
________________________________________________________________________

*Модели данных Pydantic* - исп-ся в body-пар-рах. Являются наследниками
класса `pydantic.BaseModel`. Просто преобразуются в JSON за счет своего
строения: по сути в простейшем виде представляет собой класс данных без
доп. методов, который представляется в виде схемы "название поля - тип
данных [- значение по умолчанию при необх-ти]". Такая схема один в один
повторяет схему объекта JSON.

Примерная схема объявления и исп-я модели:

```py
from pydantic import BaseModel


class ModelName(BaseModel):
    param_name1: param_type1 [= default_val1]
    param_name2: param_type2 [= default_val2]
    ...

...

@app.post('/some/endpoint')
async def some_function(some_param: ModelName):
    ...
```
________________________________________________________________________

Возьмем пример из раздела про body-пар-ры:

```py
...

class Item(BaseModel):
    name: str
    description: str | None = None
    price: float

...

@app.post('/items/')
async def post_item(item: Item):
    return item
```

Здесь Item - модель данных (ТД и обязательность полей которой
описывается аналогично query-пар-рам, а также может тоже принимать ТД
модели данных), а item в ф-ции - body-пар-р.

Рассмотрим Item для наглядности в JSON нотации, получающегося после
преобразований:

```json
// подходит
{
    "name": "watermelon",
    "description": "Beautiful fruit (or berry?)",
    "price": 30
}

// подходит
{
    "name": "apple",
    "price": 150
}

// не подходит
{
    "name": "melon",
    "description": "Where's a water?"
}

// не подходит
{
    "name": "Alex",
    "surname": "Brown",
    "birthday": "01.01.1991"
}
```
________________________________________________________________________

FastAPI автоматически проведет валидацию модели как и любого другого ТД,
а также добавит ее в автоматическую документацию в виде JSON Schema. В
то же время, моделью можно пользоваться как любым другим классом данных
в Python через обращение `экземпляр.параметр` или `класс.параметр`.

Кроме того, стоит отметить, что FastAPI позволяет работать с моделями
любой глубины вложенности. Т.о. можно объявить, например, одно из полей
как список, множество или представителя другой модели.
________________________________________________________________________

### ВИДЫ ПАРАМЕТРОВ ###

### <u> Path-параметры </u> ###

*Path-параметры* - пар-ры, которые передаются в составе адреса
эндпоинта. Задаются через форматирование строк Python. Самый базовый вид
на примере ID предмета:

```py
@app.get('/items/{item_id}')  # item_id - path-параметр
async def get_item(item_id):
    return {'item_id': item_id}
```
________________________________________________________________________

С path-пар-рами можно:

- Задать тип данных, чтобы Pydantic автоматически проверял и переводил
    пар-р в нужный ТД, а в случае невозможности выдавал ошибку. Можно
    исп-ть простые типы данных Python и Enum-дочерние ТД. На предыдущем
    примере:

    ```py
    @app.get('/items/{item_id}')
    async def get_item(item_id: int):
        ...
    ```

    Особый случай - содержание в path-параметре к-л пути. Для него надо
    указать доп. пар-р форматирования в URL, а сам пар-р объявлять str,
    иначе FastAPI не поймет, что этот путь надо считать как пар-р, а
    будет искать соотв. эндпоинт. Например:

    ```py
    @app.get('/items/{item_path:path}')  # доп. пар-р "path"
    async def get_item(item_path: str):
        ...
    ```

    Теперь "127.0.0.1:8000/items/dir/subdir/file.txt" сработает, а
    item_path примет значение "items/dir/subdir/file.txt".

- Определять доп. информацию и выполнять доп. валидацию с помощью
    `typing.Annotated` и `fastapi.Path`. Об этом - см. в "Расширенная
    аннотация и валидация".

- Комбинировать другие типы пар-ров.
________________________________________________________________________

Порядок объявления пар-ров имеет значение. Т.о. если есть некоторое
станд. фикс. значение для пар-ра со своей логикой, то нужно объявить
логику для фикс. значения первее. Иначе FastAPI, пробегаясь по списку
эндпоинтов в порядке их объявления в коде, не дойдет до логики фикс.
значения, постарается обработать его общей логикой и даст ответ согласно
общей логике.

Например:

```py
...

@app.get('/users/me')
async def get_me():
    ...

@app.get('/users/{user_id}')
async def get_user(user_id: int):
    ...

...
```

В таком порядке все работает как ожидается. Но если объявить наоборот,
то FastAPI дойдет до общей логики с user_id первее, воспримет "me" как
значение user_id и обработает его, выдав ошибку, т.к. "me" не является
int.
________________________________________________________________________

### <u> Query-параметры </u> ###

*Query-параметры* - именованные пар-ры, передаваемые после эндпоинта и
знака `?`, разделенные между собой знаком `&`. Любые пар-ры ф-ции в
Python, не являющиеся пар-рами пути, интерпретируются как query-пар-ры
(за исключением следующих категорий пар-ров). Пример базового вида:

```py
@app.get('/items/')
async def get_item(item_filter, onpage):
    return {'filter': item_filter, 'onpage': onpage}
```

Для такого эндпоинта запрос по адресу
"127.0.0.1:8000/items/?item_filter=some_filter&onpage=10" даст ответ
"{'filter': 'some_filter', 'onpage': '10'}".
________________________________________________________________________

С query-пар-рами можно:

- Задать ТД по аналогии с path-пар-рами (простые ТД, Enum-дочерние).

- Задать значение по умолчанию так же, как обычно в ф-циях Python.

- Сделать их обязательными или необязательными: если значение по
    умолчанию не задано, то пар-р обязателен, иначе - необязателен.

    Например для последних 3 пунктов:

    ```py
    @app.get('/items/')
    async def get_item(comment: str, item_filter: str | None = None,
                       onpage: int = 10):
        return {'filter': item_filter, 'onpage': onpage,
                'comment': comment}
    ```

    Здесь comment - обязательный, item_filter - необязательный, но
    значение по умолчанию None, для отдельной обработки случая без
    указания данного пар-ра, onpage - необязательный, значение по
    умолчанию 10, обрабатывается одинаково как при указании, так и при
    неуказании данного пар-ра в запросе.

- Определять доп. информацию и выполнять доп. валидацию с помощью
    `typing.Annotated` и `fastapi.Query`. Об этом - см. в "Расширенная
    аннотация и валидация".

- Комбинировать другие типы пар-ров.
________________________________________________________________________

### <u> Body-параметры </u> ###

*Body-параметры* - пар-ры, передаваемые в теле запроса. Задаются так же,
как query-пар-ры, но с помощью моделей данных Pydantic - по тому,
"скалярный" или модельный ТД имеет пар-р, FastAPI и различает query- и
body-пар-ры.

Исп-ся с запросами POST, PUT, DELETE, PATCH. И хотя в крайнем случае
можно исп-ть и с другими (FastAPI поддерживает такую возм-ть), поведение
запросов наподобие GET при наличии тела не определено в спецификациях и
может не поддерживаться некоторыми прокси-серверами, что по дороге от
клиента до сервера сломает запрос. Поэтому рекомендуется исп-ть
body-пар-ры только с POST, PUT, DELETE, PATCH.
________________________________________________________________________

Объявление модели данных Pydantic подробнее описано в разделе "Типы
данных" настоящего конспекта. Здесь ограничимся кратким примером:

```py
...

class Item(BaseModel):
    name: str
    description: str | None = None
    price: float

...

@app.post('/items/')
async def post_item(item: Item):
    return item
```

Здесь item - body-пар-р, имеющий ТД Item - модели данных, унаследованной
от pydantic.BaseModel. Данный пар-р будет передаваться не в строке URL
запроса, а в его теле.
________________________________________________________________________

С body-пар-рами можно:

- Указывать несколько штук - тогда отдельные JSON-представления
    при передаче объединятся в одно тело с ключами - именами пар-ров. В
    коде Python же все будет работать раздельно, как обычно.

- Определять доп. информацию и выполнять доп. валидацию с помощью
    `typing.Annotated` и `fastapi.Body`. Кроме того, можно объявлять
    body-пар-ры простых ТД с помощью Annotated. Об этом - см. в
    "Расширенная аннотация и валидация".

- Комбинировать другие типы пар-ров.

### РАСШИРЕННАЯ АННОТАЦИЯ И ВАЛИДАЦИЯ ###

Расширенная аннотация и валидация позволяет более точно настроить онные
процессы и добавить метаданные. Производится посредством
`typing.Annotated` и доп. класса соотв. вида пар-ра (`fastapi.Path`,
`fastapi.Query` и др.). Рассмотрим на примере query-пар-ров, для
остальных - по аналогии и в соответствии с их функционалом. Разница по
необх-ти будет указана в конце данного раздела конспекта.
________________________________________________________________________

Общий синтаксис: сначала инлайн-аннотацию передаваемого атрибута ф-ции
надо обернуть в Annotated, а затем добавить Query с его пар-рами для
аннотации и валидации.

Пример с проверкой, что длина строки не превышает 50 символов:

```py
from typing import Annotated
from fastapi import FastAPI, Query

app = FastAPI()


@app.get('/')
async def get_root(q: Annotated[str | None, Query(max_length=50)] = None):
    ...
```

В случае невыполнения требования выдаст ошибку. Этот пример также
показывает взаимодействие с оговоренными выше вещами (значение по
умолчанию, обязательные и необязательные пар-ры) - все работает точно
так же, но аннотация ТД оборачивается в конструкцию Annotated + Query.
________________________________________________________________________

Т.о. можно:

- Задавать пар-р как список с помощью `Annotated[list[<type>], Query()]`
    (см. подробнее в "Типы данных").

- Для строк:
    - Задавать мин. и макс. длину ч/ пар-ры Query `min_length` и
        `max_length`.
    - Задавать регулярное выражение для проверки на соответствие ему с
        помощью пар-ра `pattern`.

- Для чисел:
    - Добавлять проверку на больше-меньше-равно к-л числа с помощью
        `gt`, `ge`, `lt`, `le`.

- Метаданные:
    - Задать `title` и `description`, маркировать пар-ры в документации
        как устаревшие ч/ `deprecated=True` или исключить из
        документации ч/ `include_in_schema=False`.
    - Добавить псевдоним пар-ра ч/ `alias`. Например, для исп-я
        символов, которые нельзя исп-ть в именах переменных Python
        (`param_name: Annotated[str, Query(alias=param-name)]` позволит
        сделать запрос вида ".../?param-name=..." и записать результат в
        пар-р param_name).

- Добавить кастомную валидацию после или до основной валидации с помощью
    `pydantic.AfterValidator` и `pydantic.BeforeValidator` соотв.
    Синтаксис следующего вида:
    `Annotated[<type>, AfterValidator(<func>)]`, где func - синхронная
    ф-ция, принимающая в себя один пар-р того же ТД, что описан в данном
    Annotated.
________________________________________________________________________

Отдельно для query-пар-ров можно:

- Исп-ть модели данных Pydantic для групп связанных пар-ров, чтобы
    единожды объявить эту модель и исп-ть ее в разных местах, а также
    упростить восприятие аннотации.
    
    Для доп. валидации полей в таком случае в модели исп-ся
    `pydantic.Field`, которому приравнивается атрибут, словно значению
    по умолчанию. Само же значение по умолчанию указывается внутри
    Field первым или с помощью атрибута `default`. Остальные пар-ры доп.
    аннотации и валидации идентичны pydantic.Query.

    Для перечисления возможных строковых значений в таком случае мб
    удобнее пользоваться `typing.Literal`, нежели Enum-дочерними
    классами.

    Кроме того, можно ограничить получаемые query-пар-ры с помощью спец.
    атрибута класса `model_config = {'extra': 'forbid'}`, запрещая иные
    query-пар-ры, кроме указанных полей в модели. Случай редкий, но
    иногда мб нужно.

    Пример:

    ```py
    ...

    class FilterParams(BaseModel):
        model_config = {'extra': 'forbid'}

        limit: int = Field(100, gt=0, le=100)
        offset: int = Field(0, ge=0)
        order_by: Literal['date', 'name'] = 'date'
        order: Literal['asc', 'desc'] = 'asc'

    @app.get('/')
    async def get_root(filter_params: Annotated[FilterParams, Query()]):
        ...
    ```

    В таком случае FastAPI соберет из URL все query-пар-ры согласно
    полям модели FilterParams и приведет их в соответствие в виде
    переменной filter_params. Кроме того, неизвестные модели
    query-пар-ры (т.е. любые с именами, не являющимися limit, offset,
    order_by и order) не пропустятся, а вызовут ошибку.
________________________________________________________________________

Отдельно для body-пар-ров:

- Добавлять валидацию отдельных полей модели можно с помощью
    `pydantic.Field`, как это показано в блоке выше для query-пар-ров.
    Именно такая расширенная валидация для body-пар-ров и исп-ся, за
    исключением аннотирования как единого целого или валидации
    body-пар-ров простых ТД.

- Annotated исп-ся для объявления body-пар-ров простых ТД наподобие int,
    str и проч. Чаще всего это исп-ся в случае нескольких body-пар-ров.

    Пример:

    ```py
    class Item(BaseModel):
        ...
    
    class User(BaseModel):
        ...

    @app.post('/')
    async def post_root(item: Item, user: User,
                        priority: Annotated[int, Body()]):
        ...
    ```

    Тогда единое представление тела запроса в формате JSON будет:

    ```json
    {
        "item": {
            ...
        },
        "user": {
            ...
        },
        "priority": ...
    }
    ```

- Ожидать обернутый одиночный body-пар-р в JSON-представлении так,
    словно пар-ров несколько, с помощью `Body(embed=True)`.

    Т.о.:

    ```json
    // вместо классического
    {
        "col1": ...,
        "col2": ...,
        ...
    }

    // ожидается
    {
        "modelname": {
            "col1": ...,
            "col2": ...,
            ...
        }
    }
    ```
