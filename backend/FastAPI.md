# ОСНОВНЫЕ ФУНКЦИИ #

## ПЕРВЫЕ ШАГИ ##

`fastapi` - модуль. Установка как стандартный пакет:
`pip install fastapi[standart]`. Содержит мн-во различных необх. для
правильной и удобной работы с FastAPI наподобие Pydantic (см. исп-е в
др. разделах данного конспекта).

`fasapi dev filename.py` - команда для терминала для запуска сервиса на
FastAPI в режиме разработчика. Для запуска в режиме продукта - убрать
`dev` в команде. В условиях расположения на локальной машине доступ
будет в браузере по адресу, который выведется в консоль (т.е. скорее
всего `127.0.0.1:8000`).

В случае наличия исключений и ошибок в таком формате запуска приложение
не крашится, а возвращает описание ошибки как полноценный HTTP-ответ в
JSON формате.
________________________________________________________________________

`app = FastAPI()` - создание приложения FastAPI.
________________________________________________________________________

*Эндпоинт* - путь после домена. По ним разделяются различные ресурсы,
операции, задачи и проч. Коренной эндпоинт - `/`, пример другого
эндпоинта: `/some/path/to/endpoint`.

Поддерживаются все HTTP-запросы: основные - POST, GET, PUT, DELETE, - и
более экзотические - OPTIONS, HEAD, PATCH, TRACE. Для каждого эндпоинта
возможна регистрация нескольких HTTP-методов.

Регистрация операции для эндпоинта (или просто регистрация эндпоинта) в
приложении FastAPI на примере GET-запроса (здесь и далее "app" -
экземпляр класса fastapi.FastAPI):

```py
@app.get('/some/path/to/endpoint')
async def some_func():
    ...  # ф-ция для обработки сервером GET-запроса к эндпоинту
    return ...
```

Как видно из примера, регистрация производится с помощью декоратора
`<имя-приложения>.<HTTP-метод>('<эндпоинт>')`. Ф-ция, оборачиваемая в
декоратор, представляет собой операцию, выполнямую по данному
HTTP-запросу. Т.к. FastAPI - асинхронный фреймворк, то и ф-ции исп-ся
обычно асинхронные, и важно поддерживать ее правильную работу. Тем не
менее, чисто технически возможно исп-е и обычных ф-ций, но с потерей
практически всех плюсов асинхронного устр-ва FastAPI.

Кроме того, довольно логино, что ф-ции следует возвращать что-то на
приходящий запрос, и ее ответ возвращается в `return`, как и в обычных
ф-циях. Поддерживаются все обычные типы данных Python, HTML-страницы,
ORM-объекты и модели Pydantic. Они автоматически преобразуются в JSON по
необх-ти для отправки как HTTP-ответа.
________________________________________________________________________

Т.о. Hello World в FastAPI:

```py
from fastapi import FastAPI

app = FastAPI()


@app.get('/')
async def helloworld():
    return {'message': 'Hello World'}
```
________________________________________________________________________

Крайне полезная вещь в разработке - автоматическая документация. Она
доступна по эндпоинту `/docs`. Там можно также опробовать
зарегистрированные эндпоинты.

Кроме того, по адресу `/openapi.json` достуна полная схема сервиса в
формате JSON.

Для автоматического документирования есть мн-во функционала, часть
которого автоматически считывает данные без доп. усилий, часть - требует
вручную что-то задать (метаданные, примеры пар-ров и др.). Некоторое
описано в данном конспекте по мере углубления в темы, но за более
подробной информацией следует обратиться к документации FastAPI или
оф. туториалу.

## ПАРАМЕТРЫ ЗАПРОСА ##

### ТИПЫ ДАННЫХ ###

### <u> Типы данных Python </u> ###

В первую очередь, с FastAPI и его автоматической валидацией работают все
простые типы данных Python и некоторые составные.

- `int`, `float` - как обычно.

- `str` - как обычно. Кроме того, можно исп-ть унаследованные от него ТД
    из Pydantic наподобие `HttpUrl` для HTTP-адресов.

- `bool` - тоже как обычно, но в запросе в качестве True принимаются
    значения: 1, True, true, on, yes и их вариации написания. Иное
    значение - False.

- `list[<type>]` - для body-пар-ров можно указывать вчистую, как обычно,
    в то время как для query-пар-ров лучше внутри typing.Annotated (см.
    соотв. блок в подтеме "Query-параметры"). Тогда может принимать
    несколько переданных значений и сложить их в один список.
    
    Пример:

    ```py
    @app.get('/')
    async def get_root(q: Annotated[list | None, Query()] = None):
        return {'q': q}
    ```

    Тут сработает запрос вида "127.0.0.1:8000/?q=aaa&q=bbb", возвращая
    "{'q': ['aaa', 'bbb']}". Для валидации ТД в списке - указать тип.

- `dict[\<key_type>, \<val_type>]` - для body-пар-ров. Исп-ся, когда
    хочется получить неизвестные ключи либо когда хочется иметь ключи
    иного от str ТД. В таком случае в передаваемом JSON-представлении
    тела запроса будет, конечно, ТД str, но FastAPI при получении
    автоматически валидирует и преобразует данные.

- `set`, `frozenset` - преобразуются в список при передаче.

- `bytes` - передается как строка.
________________________________________________________________________

FastAPI также работает с некоторыми более специфическими типами данных:

- `UUID` - станд. универсальный уникальный идентификатор, при передаче
    преобразуется в строку.

- ТД из библиотеки `datetime` - `datetime`, `date`, `time` передаются
    как строки, а `timedelta` - как float.
________________________________________________________________________

В качестве ТД мб использованы *классы, дочерние классу `enum.Enum`*, с
перечислением возможных значений. Так можно ограничить возможные
значения до списка разрешенных, а также пользоваться Enum-дочерним
классом при обработке запроса с проверкой `is` или получая значение ч/
атрибут `value`.

Например:

```py
from enum import Enum

...

class SiteTheme(str, Enum):
    dark = 'dark'
    light = 'light'
    festive = 'festive'

...

@app.get('/')
async def root(theme: SiteTheme):
    msg = f'Hi!'
    if theme is SiteTheme.festive:
        msg = f'{msg} Happy Holidays!'
    return {'message': f'{msg} Theme now: {theme.value}.',
            'theme': theme}
```

Как видно, в ответе можно исп-ть без атрибута value, если передавать
непосредственно theme, т.к. FastAPI сам преобразует theme в его значение
str согласно SiteTheme для передачи в стандарте JSON.

Примеры запросов:

- `127.0.0.1:8000/?theme=dark` - работает, ответ:
    `{'message': 'Hi! Theme now: dark.', 'theme': 'dark'}`.
- `127.0.0.1:8000/?theme=midnight-blue` - ошибка.
- `127.0.0.1:8000/?theme=festive` - работает, ответ:
    `{'message': 'Hi! Happy Holidays! Theme now: festive.', 'theme': 'festive'}`
________________________________________________________________________

### <u> Модели данных Pydantic </u> ###

*Модели данных Pydantic* - исп-ся в body-пар-рах. Являются наследниками
класса `pydantic.BaseModel`. Просто преобразуются в JSON за счет своего
строения: по сути в простейшем виде представляет собой класс данных без
доп. методов, который представляется в виде схемы "название поля - тип
данных [- значение по умолчанию при необх-ти]". Такая схема один в один
повторяет схему объекта JSON.

Примерная схема объявления и исп-я модели:

```py
from pydantic import BaseModel


class ModelName(BaseModel):
    param_name1: param_type1 [= default_val1]
    param_name2: param_type2 [= default_val2]
    ...

...

@app.post('/some/endpoint')
async def some_function(some_param: ModelName):
    ...
```
________________________________________________________________________

Возьмем пример из раздела про body-пар-ры:

```py
...

class Item(BaseModel):
    name: str
    description: str | None = None
    price: float

...

@app.post('/items/')
async def post_item(item: Item):
    return item
```

Здесь Item - модель данных (ТД и обязательность полей которой
описывается аналогично query-пар-рам, а также может тоже принимать ТД
модели данных), а item в ф-ции - body-пар-р.

Рассмотрим Item для наглядности в JSON нотации, получающегося после
преобразований:

```json
// подходит
{
    "name": "watermelon",
    "description": "Beautiful fruit (or berry?)",
    "price": 30
}

// подходит
{
    "name": "apple",
    "price": 150
}

// не подходит
{
    "name": "melon",
    "description": "Where's a water?"
}

// не подходит
{
    "name": "Alex",
    "surname": "Brown",
    "birthday": "01.01.1991"
}
```
________________________________________________________________________

FastAPI автоматически проведет валидацию модели как и любого другого ТД,
а также добавит ее в автоматическую документацию в виде JSON Schema. В
то же время, моделью можно пользоваться как любым другим классом данных
в Python через обращение `экземпляр.параметр` или `класс.параметр`.

Кроме того, стоит отметить, что FastAPI позволяет работать с моделями
любой глубины вложенности. Т.о. можно объявить, например, одно из полей
как список, множество или представителя другой модели.
________________________________________________________________________

*Специальные модели и ТД Pydantic* - модели и ТД, прописанные в самом
Pydantic или его расширениях.

- `EmailStr` - строка с имейлом (с валидацией). Требует доп. установки
    `email-validator`: `pip install email-validator` или
    `pip install pydantic[email]`.
________________________________________________________________________

### <u> Передача файлов </u> ###

> **ВАЖНО!** Файлы передаются как данные формы, поэтому для начала
следует изучить темы "Form-параметры" и "Расширенная аннотация и
валидация", а затем вернуться к этой теме. По этой же причине для исп-я
нужно установить `python-multipart`: `pip install python-multipart`.

Файлы передаются по аналогии с form-пар-рами, словно отдельный
file-пар-р: ч/ `typing.Annotated` и `fastapi.File` (является дочерним
классу Form), при этом ТД пар-ра в Annotated указывается как bytes. Есть
иной вариант - задать ТД как `fastapi.UploadFile` - File тогда не
обязателен.

Примеры:

```py
@app.post('/files/')
async def post_file(file: Annotated[bytes, File()]):
    ...

@app.post('/uploadfile/')
async def post_uploadfile(file: UploadFile):
    ...
```
________________________________________________________________________

Задание ч/ File подходит для небольших файлов, т.к. загружаются сразу в
память в формате bytes. Загрузка ч/ UploadFile позволяет исп-ть
"буферный" файл - файл, хранящийся до максимального предела размера в
памяти, после преодоления предела - на диске. Т.о. UploadFile подходит и
для больших файлов. Кроме того, UploadFile позволяет получить метаданные
из файла, реализует file-like async интерфейс и представляет собой
реальный объект Python - `SpooledTemploraryFile`, - который можно исп-ть
с другими библиотеками Python.

Поэтому преимущественно лучше UploadFile, но даже в таком случае File
нам еще пригодится.
________________________________________________________________________

UploadFile имеет:

- Атрибуты:
    - `filename` - имя файла с расширением в формате str.
    - `content_type` - тип содержимого в формате str вида MIME/media
        (например, "image/jpeg").
    - `file` - SpooledTemploraryFile file-like объект для исп-я в др.
        ф-циях и библиотеках.

- Методы (async):
    - `write(<data>)` - записать данные data формата str или bytes в
        файл.
    - `read(<size>)` - прочитать size формата int байт или символов из
        файла.
    - `seek(<offset>)` - перейти к байту на позиции offset формата int.
    - `close()` - закрыть файл.

- Фичи:
    - Можно задать метаданные и проч. с помощью Annotated и File:
        `Annotated[UploadFile, File(...)]`.
    - Можно исп-ть в list для загрузки нескольких файлов.
________________________________________________________________________

Также добавим пример HTML-формы (с методом POST) для загрузки файлов:

```html
<body>
    <form action="/some/endpoint" enctype="multipart/form-data" method="post">
        <input name="some_name" type="file" multiple>
        <input type="submit">
    </form>
</body>
```

Данный пример подойдет как для File, так и для UploadFile. Кроме того,
стоит обратить внимание на атрибут `multiple`, позволяющий загрузить
несколько файлов. Для одного - убрать атрибут.
________________________________________________________________________

Для получения доп. данных помимо файлов лучше исп-ть данные формы с
помощью Form (см. "Form-параметры") и нельзя исп-ть body-пар-ры, т.к.
File - подкласс Form.
________________________________________________________________________

### ВИДЫ ПАРАМЕТРОВ ###

### <u> Path-параметры </u> ###

*Path-параметры* - пар-ры, которые передаются в составе адреса
эндпоинта. Задаются через форматирование строк Python. Самый базовый вид
на примере ID предмета:

```py
@app.get('/items/{item_id}')  # item_id - path-параметр
async def get_item(item_id):
    return {'item_id': item_id}
```
________________________________________________________________________

С path-пар-рами можно:

- Задать тип данных, чтобы Pydantic автоматически проверял и переводил
    пар-р в нужный ТД, а в случае невозможности выдавал ошибку. Можно
    исп-ть простые типы данных Python и Enum-дочерние ТД. На предыдущем
    примере:

    ```py
    @app.get('/items/{item_id}')
    async def get_item(item_id: int):
        ...
    ```

    Особый случай - содержание в path-параметре к-л пути. Для него надо
    указать доп. пар-р форматирования в URL, а сам пар-р объявлять str,
    иначе FastAPI не поймет, что этот путь надо считать как пар-р, а
    будет искать соотв. эндпоинт. Например:

    ```py
    @app.get('/items/{item_path:path}')  # доп. пар-р "path"
    async def get_item(item_path: str):
        ...
    ```

    Теперь "127.0.0.1:8000/items/dir/subdir/file.txt" сработает, а
    item_path примет значение "items/dir/subdir/file.txt".

- Определять доп. информацию и выполнять доп. валидацию с помощью
    `typing.Annotated` и `fastapi.Path`. Об этом - см. в "Расширенная
    аннотация и валидация".

- Комбинировать другие типы пар-ров.
________________________________________________________________________

Порядок объявления пар-ров имеет значение. Т.о. если есть некоторое
станд. фикс. значение для пар-ра со своей логикой, то нужно объявить
логику для фикс. значения первее. Иначе FastAPI, пробегаясь по списку
эндпоинтов в порядке их объявления в коде, не дойдет до логики фикс.
значения, постарается обработать его общей логикой и даст ответ согласно
общей логике.

Например:

```py
...

@app.get('/users/me')
async def get_me():
    ...

@app.get('/users/{user_id}')
async def get_user(user_id: int):
    ...

...
```

В таком порядке все работает как ожидается. Но если объявить наоборот,
то FastAPI дойдет до общей логики с user_id первее, воспримет "me" как
значение user_id и обработает его, выдав ошибку, т.к. "me" не является
int.
________________________________________________________________________

### <u> Query-параметры </u> ###

*Query-параметры* - именованные пар-ры, передаваемые после эндпоинта и
знака `?`, разделенные между собой знаком `&`. Любые пар-ры ф-ции в
Python, не являющиеся пар-рами пути, интерпретируются как query-пар-ры
(за исключением следующих категорий пар-ров). Пример базового вида:

```py
@app.get('/items/')
async def get_item(item_filter, onpage):
    return {'filter': item_filter, 'onpage': onpage}
```

Для такого эндпоинта запрос по адресу
"127.0.0.1:8000/items/?item_filter=some_filter&onpage=10" даст ответ
"{'filter': 'some_filter', 'onpage': '10'}".
________________________________________________________________________

С query-пар-рами можно:

- Задать ТД по аналогии с path-пар-рами (простые ТД, Enum-дочерние).

- Задать значение по умолчанию так же, как обычно в ф-циях Python.

- Сделать их обязательными или необязательными: если значение по
    умолчанию не задано, то пар-р обязателен, иначе - необязателен.

    Например для последних 3 пунктов:

    ```py
    @app.get('/items/')
    async def get_item(comment: str, item_filter: str | None = None,
                       onpage: int = 10):
        return {'filter': item_filter, 'onpage': onpage,
                'comment': comment}
    ```

    Здесь comment - обязательный, item_filter - необязательный, но
    значение по умолчанию None, для отдельной обработки случая без
    указания данного пар-ра, onpage - необязательный, значение по
    умолчанию 10, обрабатывается одинаково как при указании, так и при
    неуказании данного пар-ра в запросе.

- Определять доп. информацию и выполнять доп. валидацию с помощью
    `typing.Annotated` и `fastapi.Query`. Об этом - см. в "Расширенная
    аннотация и валидация".

- Комбинировать другие типы пар-ров.
________________________________________________________________________

### <u> Body-параметры </u> ###

*Body-параметры* - пар-ры, передаваемые в теле запроса. Задаются так же,
как query-пар-ры, но с помощью моделей данных Pydantic - по тому,
"скалярный" или модельный ТД имеет пар-р, FastAPI и различает query- и
body-пар-ры.

Исп-ся с запросами POST, PUT, DELETE, PATCH. И хотя в крайнем случае
можно исп-ть и с другими (FastAPI поддерживает такую возм-ть), поведение
запросов наподобие GET при наличии тела не определено в спецификациях и
может не поддерживаться некоторыми прокси-серверами, что по дороге от
клиента до сервера сломает запрос. Поэтому рекомендуется исп-ть
body-пар-ры только с POST, PUT, DELETE, PATCH.
________________________________________________________________________

Объявление модели данных Pydantic подробнее описано в разделе "Типы
данных" настоящего конспекта. Здесь ограничимся кратким примером:

```py
...

class Item(BaseModel):
    name: str
    description: str | None = None
    price: float

...

@app.post('/items/')
async def post_item(item: Item):
    return item
```

Здесь item - body-пар-р, имеющий ТД Item - модели данных, унаследованной
от pydantic.BaseModel. Данный пар-р будет передаваться не в строке URL
запроса, а в его теле.
________________________________________________________________________

С body-пар-рами можно:

- Указывать несколько штук - тогда отдельные JSON-представления
    при передаче объединятся в одно тело с ключами - именами пар-ров. В
    коде Python же все будет работать раздельно, как обычно.

- Определять доп. информацию и выполнять доп. валидацию с помощью
    `typing.Annotated` и `fastapi.Body`. Кроме того, можно объявлять
    body-пар-ры простых ТД с помощью Annotated. Об этом - см. в
    "Расширенная аннотация и валидация".

- Комбинировать другие типы пар-ров.
________________________________________________________________________

### <u> Cookie-параметры </u> ###

*Cookie-параметры* - пар-ры, содержащие в себе куки.

Объявляются сугубо ч/ `fastapi.Cookie` и `Annotated[..., Cookie()]`,
т.к. иначе они интерпретируются FastAPI как query- или body-пар-ры.
Работа с Annotated и Cookie описана в подразделе "Расширенная аннотация
и валидация" данного конспекта.

Стоит заметить, что особенности обработки куки браузерами не позволяют
JS получать к ним доступ, а это, в свою очередь, не позволяет проверять
работоспособность HTTP-методов в автоматической документации, т.к. UI
работает с JS. Тем не менее, информация в документации о cookie-пар-рах
содержаться будет, как и о любых других пар-рах.

Хорошей и частой практикой для cookie-пар-ров будет исп-е моделей
Pydantic. Для больших подробностей - см. "Расширенная аннотация и
валидация".
________________________________________________________________________

Добавим небольшую справку по куки.

*Cookie* (куки) - это небольшие текстовые файлы с информацией о
пользователе, которые хранятся на его устр-ве, в папке браузера. Они
позволяют сайту узнавать пользователя и настраивать под него сессию. В
себе они могут содержать авторизационные данные, информацию о регионе,
устр-ве, теме, статистику активности и проч.

Пример простого файла куки:

```
HTTP/1.0 200 OK
Content-type: text/ html
Set-Cookie: theme=dark
Set-Cookie: sessionToken=abc123; Expires=Ср., 15 августа 2024 г. 12:19:26 GMT
```
________________________________________________________________________

Работает в следующем порядке:

1. Браузер нового посетителя сайта делает запрос на сервер.
2. Сайт передает браузеру файлы куки с данными для идентификации.
3. При повторном входе на сайт браузер отправляет ему полученные куки.
4. Сайт персонализирует страницу с учетом полученных данных и отправляет
    ответ браузеру
________________________________________________________________________

Основные ф-ции:

- Управление сессиями - передача статуса аутентификации, информация для
    работы сайта по действиям пользователя.

- Персонализация - сохранение настроек пользователя для отправки на
    сервер и возвращения уже готового решения в виде HTML-страницы с
    выбранными настройками персонализации.

- Отслеживание действий пользователя - для статистики или релевантной
    рекламы. Делайтеся это ч/ уникальный ID, присваиваемый пользователю
    при первом посещении, и дальнейшее отслеживание сервером посещенных
    страниц в пределах данного сайта или системы.
________________________________________________________________________

### <u> Header-параметры </u> ###

*Header-параметры* - параметры заголовка.

Объявляются сугубо ч/ `fastapi.Header` и `Annotated[..., Header()]`,
т.к. иначе они интерпретируются FastAPI как query- или body-пар-ры.
Подробно работа с Annotated и Header описана в подразделе "Расширенная
аннотация и валидация" данного конспекта.

Хорошей и частой практикой для header-пар-ров будет исп-е моделей
Pydantic. Для больших подробностей - см. "Расширенная аннотация и
валидация".
________________________________________________________________________

### <u> Form-параметры </u> ###

*Form-параметры* - это не столько пар-ры, сколько формат передаваемых
данных: вместо JSON - поля HTML-формы. За счет этого нельзя вместе с
form-пар-рами передавать body-пар-ры, кодированные через JSON.

Для исп-я нужно установить `python-multipart`:
`pip install python-multipart`.

Объявляются сугубо ч/ `fastapi.Form` и `Annotated[..., Form()]`, т.к.
иначе они интерпретируются FastAPI как query- или body-пар-ры. Подробно
работа с Annotated и Form описана в подразделе "Расширенная аннотация и
валидация" данного конспекта.

Хорошей и частой практикой для полей формы будет исп-е моделей Pydantic.
Для больших подробностей - см. "Расширенная аннотация и валидация".
________________________________________________________________________

Обсудим поля HTML-формы. Обычно такие поля, задающиеся внутри
`<form></form>`, исп-т специальное кодирование, отличное от JSON.
FastAPI гарантирует правильное чтение этих данных при правильном исп-ии.

Зачем поля формы? Ряд различных протоколов и инструментов требует по
своей спецификации именно поля формы для своей правильной работы.
Например, в одном из способов исп-я OAuth2 обязательно требуется 2 поля
формы со строго заданными именами: username и password.
________________________________________________________________________

### РАСШИРЕННАЯ АННОТАЦИЯ И ВАЛИДАЦИЯ ###

Расширенная аннотация и валидация позволяет более точно настроить онные
процессы и добавить метаданные. Производится посредством
`typing.Annotated` и доп. класса соотв. вида пар-ра (`fastapi.Path`,
`fastapi.Query` и др.). Рассмотрим на примере query-пар-ров, для
остальных - по аналогии и в соответствии с их функционалом. Разница по
необх-ти будет указана в конце данного раздела конспекта.
________________________________________________________________________

Общий синтаксис: сначала инлайн-аннотацию передаваемого атрибута ф-ции
надо обернуть в Annotated, а затем добавить Query с его пар-рами для
аннотации и валидации.

Пример с проверкой, что длина строки не превышает 50 символов:

```py
from typing import Annotated
from fastapi import FastAPI, Query

app = FastAPI()


@app.get('/')
async def get_root(q: Annotated[str | None, Query(max_length=50)] = None):
    ...
```

В случае невыполнения требования выдаст ошибку. Этот пример также
показывает взаимодействие с оговоренными выше вещами (значение по
умолчанию, обязательные и необязательные пар-ры) - все работает точно
так же, но аннотация ТД оборачивается в конструкцию Annotated + Query.
________________________________________________________________________

Т.о. можно:

- Задавать пар-р как список с помощью `Annotated[list[<type>], Query()]`
    (см. подробнее в "Типы данных").

- Для строк:
    - Задавать мин. и макс. длину ч/ пар-ры Query `min_length` и
        `max_length`.
    - Задавать регулярное выражение для проверки на соответствие ему с
        помощью пар-ра `pattern`.

- Для чисел:
    - Добавлять проверку на больше-меньше-равно к-л числа с помощью
        `gt`, `ge`, `lt`, `le`.

- Метаданные:
    - Задать `title` и `description`, маркировать пар-ры в документации
        как устаревшие ч/ `deprecated=True` или исключить из
        документации ч/ `include_in_schema=False`.
    - Добавить псевдоним пар-ра ч/ `alias`. Например, для исп-я
        символов, которые нельзя исп-ть в именах переменных Python
        (`param_name: Annotated[str, Query(alias=param-name)]` позволит
        сделать запрос вида ".../?param-name=..." и записать результат в
        пар-р param_name).

- Добавить кастомную валидацию после или до основной валидации с помощью
    `pydantic.AfterValidator` и `pydantic.BeforeValidator` соотв.
    Синтаксис следующего вида:
    `Annotated[<type>, AfterValidator(<func>)]`, где func - синхронная
    ф-ция, принимающая в себя один пар-р того же ТД, что описан в данном
    Annotated.

- Добавлять примеры пар-ров или полей для автоматической документации ч/
    `examples` и `openapi_examples` (подробнее - см. официальный
    туториал, тема "Объявление примеров данных запросов").
________________________________________________________________________

Кроме того, можно исп-ть модели данных Pydantic для групп связанных
пар-ров, чтобы единожды объявить эту модель и исп-ть ее в разных местах,
а также чтобы упростить восприятие аннотации.

Для доп. валидации полей в таком случае в модели исп-ся
`pydantic.Field`, которому приравнивается атрибут, словно значению по
умолчанию. Само же значение по умолчанию указывается внутри Field первым
или с помощью атрибута `default`. Остальные пар-ры доп. аннотации и
валидации идентичны pydantic.Query.

Для перечисления возможных строковых значений в таком случае мб удобнее
пользоваться `typing.Literal`, нежели Enum-дочерними классами.

Кроме того, можно ограничить получаемые query-пар-ры с помощью спец.
атрибута класса `model_config = {'extra': 'forbid'}`, запрещая иные
query-пар-ры, кроме указанных полей в модели. Случай редкий, но иногда
мб нужно.

Пример:

```py
...

class FilterParams(BaseModel):
    model_config = {'extra': 'forbid'}

    limit: int = Field(100, gt=0, le=100)
    offset: int = Field(0, ge=0)
    order_by: Literal['date', 'name'] = 'date'
    order: Literal['asc', 'desc'] = 'asc'

@app.get('/')
async def get_root(filter_params: Annotated[FilterParams, Query()]):
    ...
```

В таком случае FastAPI соберет из URL все query-пар-ры согласно полям
модели FilterParams и приведет их в соответствие в виде переменной
filter_params. Кроме того, неизвестные модели query-пар-ры (т.е. любые с
именами, не являющимися limit, offset, order_by и order) не пропустятся,
а вызовут ошибку.

Еще стоит сказать, что ч/ model_config можно добавлять примеры данных
полей для автоматической документации (подробнее - см. официальный
туториал, тема "Объявление примеров данных запросов").
________________________________________________________________________

Отдельно для body-пар-ров:

- Добавлять валидацию отдельных полей модели можно с помощью
    `pydantic.Field`, как это показано в блоке выше на примере
    query-пар-ров. В отличие от последних, для body-пар-ров это носит
    не хар-р объединения, а чистой валидации и основного способа задния
    схемы body-пар-ра. Именно такая расширенная валидация для
    body-пар-ров и исп-ся, за исключением аннотирования как единого
    целого или валидации body-пар-ров простых ТД.

- Annotated исп-ся для объявления body-пар-ров простых ТД наподобие int,
    str и проч. Чаще всего это исп-ся в случае нескольких body-пар-ров.

    Пример:

    ```py
    class Item(BaseModel):
        ...
    
    class User(BaseModel):
        ...

    @app.post('/')
    async def post_root(item: Item, user: User,
                        priority: Annotated[int, Body()]):
        ...
    ```

    Тогда единое представление тела запроса в формате JSON будет:

    ```json
    {
        "item": {
            ...
        },
        "user": {
            ...
        },
        "priority": ...
    }
    ```

- Ожидать обернутый одиночный body-пар-р в JSON-представлении так,
    словно пар-ров несколько, с помощью `Body(embed=True)`.

    Т.о.:

    ```json
    // вместо классического
    {
        "col1": ...,
        "col2": ...,
        ...
    }

    // ожидается
    {
        "modelname": {
            "col1": ...,
            "col2": ...,
            ...
        }
    }
    ```
________________________________________________________________________

Отдельно для cookie-пар-ров:

- Исп-е моделей Pydantic также носит хар-р объединения нескольких для
    исп-я одного набора в разных местах и валидации в таком случае. Это
    является частой и хорошей практикой.
________________________________________________________________________

Отдельно для header-пар-ров:

- По умолчанию Header преобразует "_" в "-", т.к. большинство заголовков
    пишется через "-", а Python такие названия для переменных не
    поддерживает (как бы автоматический элиас для пар-ра). Можно
    отключить с помощью `convert_underscores=False` в Header.

- HTTP-заголовки не чувствительны к регистру, поэтому можно исп-ть в
    Python стандартный стриль наименований (т.е., например, для пар-ра
    User-Agent можно исп-ть, объединяя с прошлым пунктом, наименование
    user_agent).

- Исп-е моделей Pydantic также носит хар-р объединения нескольких для
    исп-я одного набора в разных местах и валидации в таком случае. Это
    является частой и хорошей практикой.
________________________________________________________________________

### ИНЪЕКЦИЯ ЗАВИСИМОСТЕЙ ###

*Инъекция зависимостей* означает, что у кода есть способ объявить
необходимые для его работы вещи - *зависимости*, - а система вне этого
кода имеет все необходимое для обеспечения коду этих зависимостей - для
*инъекции* этих зав-тей.

В случае FastAPI участком кода является ф-ция обработки пути, зав-тью -
некоторые ограничения или обработки, требуемые для пар-ров перед их
поступлением в ф-цию, а сам FastAPI обеспечивает инъекцию.

Это много где полезно, в частности при необх-ти обеспечить общую логику,
разелить соединения с БД, обеспечить безопасность, аутентификацию, роли,
и многое др.
________________________________________________________________________

Структура:

- Зав-тью может выступать любой callable-объект (ф-ция или класс,
    например), которые принимают те же пар-ры, что и ф-ция обработки
    пути, с теми же возможными вариациями и использованием расширенной
    аннотации и валидации.

    На базовом уровне можно считать, что валидация уже своего рода
    инъекция зав-тей, но стандартная, на уровне бибилиотеки.

- Для инъекции исп-ся `typing.Annotated` и `fastapi.Depends`, довольно
    схоже с раширенной аннотацией пар-ров. Только Depends в первую
    очередь принимает в себя объект-зав-ть (не результат вызова, а сам
    callable-объект).

    Т.о. можно, помимо всего прочего, обеспечивать и вложенность
    инъекций, где один из или более пар-ров зав-ти сами прописаны ч/
    Depends и требуют инъекции, и т.д.

- FastAPI же обеспечит, чтобы инъекция сработала каждый раз, когда
    приходит запрос. Он вызовет зав-ть, выполнит, получит результат и
    подставит в пар-р ф-ции обработки пути.
________________________________________________________________________

Начнем с простого примера. Данный пример неэффективен, т.к. уже было
оговорено ранее, как проще и быстрее реализовать тот же функционал, но
в данном случае будет просто и наглядно показать инъекцию зав-тей именно
так.

```py
from fastapi import Depends, FastAPI

...

async def common_params(q: str | None = None, skip: int = 0,
                        limit: int = 100) -> dict:
    return {'q': q, 'skip': skip, 'limit': limit}

@app.get('/items/')
async def get_items(commons: Annotated[dict, Depends(common_params)]):
    ...

@app.get('/users/')
async def get_users(commons: Annotated[dict, Depends(common_params)]):
    ...
```

common_params - зав-ть в виде ф-ции. По синтаксису, как видно, она схожа
с операциями пути, принимая те же пар-ры, но без декоратора. В get_items
и get_users производится инъекция зав-ти согласно синтаксису с
Annotated, где ТД согласуется с возвращаемым от ф-ции-зав-ти.

Обе ф-ции показаны для акцента на том, что теперь полученную зав-ть
можно исп-ть неоднократно.

Зависимость в данном случае лишь собирает пар-ры (теперь по эндпоинтам
можно указать необязательные query-пар-ры q, skip и limit), упаковывает
их в словарь и возвращает его. Неэффективно, но наглядно для базового
синтаксиса. Тем более, очевидно, в зав-ть можно вписать много другого
кода, в чем и есть ее польза.

Еще важно заметить: ф-ция-зав-ть не вызывается нигде напрямую, ее
запускает сам FastAPI. Это отличительная черта паттерна "Инъекция
зав-ти".
________________________________________________________________________

В примере выше есть неудобное повторение кода с Annotated. Можно исп-ть
переменную для обозначения всей консрукции как типа:

```py
CommonDep = Annotated[dict, Depends(common_params)]

@app.get('/items/')
async def get_items(commons: CommonDep):
    ...
```
________________________________________________________________________

Теперь используем класс в качестве зав-ти:

```py
class CommonParams:
    def __init__(q: str | None = None, skip: int = 0, limit: int = 100):
        self.q = q
        self.skip = skip
        self.limit = limit


@app.get('/items/')
async def get_items(commons: Annotated[CommonParams, Depends(CommonParams)]):
    ...
```

В таком ключе вместо неудобного словаря со стороны поддержки редактора
имеем класс, в котором можно обращаться по имени пар-ра, т.к. в пар-ре
commons ф-ции get_items будет экземпляр класса CommonParams, а не
словарь, при этом с сохранением инъекции зав-тей.
________________________________________________________________________

Снова есть повторение кода, в этот раз внутри Annotated дважды
встречается CommonParams.

Во-первых, первое CommonParams не определяет итоговый ТД, т.к. его
FastAPI возьмет из Depends. Так что чисто технически можно указать
вместо первого CommonParams Any, но тогда потеряется поддержка редактора
кода.

Во-вторых, видим повторения. Чтобы этого избежать, FastAPI предлагает
упрощение для случаев, когда зав-ть - конкретный класс:

```py
@app.get('/items/')
async def get_items(commons: Annotated[CommonParams, Depends()]):
    ...
```
________________________________________________________________________

Пример вложения зав-тей:

```py
async def dependency_inner(p1: str | None = None, p2: int = 556) -> rtype:
    ...

async def dependency_outer(q1: Annotated[rtype, Depends(dependency_inner)],
                           q2: str | None = None) -> some_type:
    ...

@app.get('/some/endpoint/')
async def get_some_endpoint(dep_param: Annotated[some_type, Depends(dependency_outer)]):
    ...
```

При этом у FastAPI есть полезная фича: если за вызов эндпоинта по той
или иной причине нужно вызвать одну и ту же зав-ть или подзав-ть
несколько раз, то вызов происходит единожды, а результат сохраняется в
кэш. Если такое не нужно - у Depends есть пар-р `use_cache=False`.
________________________________________________________________________

В некоторых случаях возвращаемое значение зав-ти не исп-ся внутри ф-ции
операции пути или зав-ть не возвращает ничего вовсе, но выполнение этой
зав-ти обязательно. Тогда можно добавить список зав-тей в пар-р
`dependencies` декоратора операции пути в виде `[Depends(dep1), ...]`.

Пример:

```py
async def verify_token(...) -> None:
    if token != 'secret-token-wooow':  # очевидно, такой проверки
                                       # "втупую" быть не должно
        raise HTTPException(...)

async def verify_key(...) -> str:
    if key != 'secret-key-wooow':
        raise HTTPException(...)
    return 'success-value'

@app.get('/', dependencies=[Depends(verify_token), Depends(verify_key)])
async def get_root():
    ...
```
________________________________________________________________________

Кроме того, зав-ти можно вносить глобально, чтобы они всегда проверялись
в каждом обращении к любому эндпоинту. Делается это с помощью пар-ра
`dependencies` класса FastAPI при создании приложения по аналогии с
декораторами операции пути.
________________________________________________________________________

Последняя фича с зав-тями - зав-ти с yield, выполняющие код после
завершения работы операции пути. Важное правило: это не генератор и не
мб в такой зав-ти больше одного yield.

Самый базовый каркас:

```py
async yield_dep():
    ...
    try:
        yield ...
    finally:
        ...
```

Здесь код выполняется до yield, последний возвращает что-то, как и в
обычной зав-ти, но после этого все не заканчивается: выполнение зав-ти
приостанавливается до тех пор, пока операция пути не отправит ответ
клиенту, а затем довыполняется блок finally.

Как видно, это своего рода контекстный менеджер (и его можно написать и
ч/ класс), и применения также схожи.
________________________________________________________________________

Важные замечания:

- Как заметка: блок try-except-finally работает, как и всегда, и весь
    его синтаксис применим.

- Блок try-except-finally отлавливает все ошибки, в т.ч. те, которые
    вызвались в операции пути, это важно помнить.

- Как заметка: иногда может понадобится отлавливание определенных
    исключений и перевызвать уже другое исключение, например,
    HTTPException как самый распространенный вариант. Чаще всего это не
    понадобится, т.к. все такие события обычно прописываются в операции
    пути или обработчике исключений. Тем не менее, может пригодиться.

- Если при отлове конкретного исключения через except (с целью ч-л
    сделать дополнительно) не вызвать повторный raise данного (или
    другого, см. предыдущий пункт) исключения, то клиенту, как и
    полагается, вернется ответ со статус-кодом 500, но вот сервер никак
    это исключение не запишет как происшествие в логи и т.д. Это
    происходит, т.к. исключение уже отловлено и обработано, а до
    "автоматики" FastAPI оно не дошло. Поэтому для таких случаев важно
    перевызывать исключение (или поднимать новое).

    Пример:

    ```py
    async def some_yield_dep():
        try:
            yield ...
        except SomeException:
            ...
            raise
        except SomeOtherException:
            ...
            raise HTTPException(...)
        ...
    ```

    SomeException перевызывется, а SomeOtherException поднимет
    HTTPException.

    Это мб крайне полезно для исключений, связанных с возвращаемым yield
    объектом, например, при работе с БД.

- Подзав-ти с yield работают так, как ожидается: стеково довыполняются
    по мере закрытия процессов, инициализированных позднее.

- У Depends для yield-зав-тей есть специальный пар-р `scope`,
    принимающий значения "function" или "request" (по умолчанию). Он
    отвечает за то, когда возвращаться к выполнению кода после yield:
    до отправления ответа (но уже после завершения работы ф-ции) или
    после (по умолчанию).

    Но важно помнить тогда про вложенность: зав-ть с "request" должна
    иметь подзав-ти только с "request" для корректной работы, а зав-ть с
    "function" может иметь любые подзав-ти.
________________________________________________________________________

## ОТВЕТЫ ##

Для ответа (указываемого после return) можно указывать ТД. Нужно это для
аннотации, валидации, ограничений и фильтрации данных. ТД для
возвращаемого ответа мб указан как с помощью средств аннотации Python,
так и с помощью пар-ра `response_model` декоратора с HTTP-методом. О
последнем - в подразделе "Модель ответа". 

В качестве ТД можно исп-ть то же, что и в пар-рах запроса (см.
"Параметры запроса" -> "Типы данных"), в т.ч. ТД Python и модели
Pydantic.
________________________________________________________________________

### МОДЕЛЬ ОТВЕТА ###

Задается с помощью пар-ра `response_model` метода приложения FastAPI с
HTTP-методом, используемым как декоратор (get, post и т.д.). Выполняет
те же ф-ции, что и аннотация возвращаемого типа, причем приоритет у
модели ответа. Но за счет последней особенности крайне нужна в
ситуациях, когда нужно вернуть данные, не соответствующие
аннотированному ТД, но требуется их к таковому привести.

Использование response_model позволяет:

- Документировать так же, как классическая аннотация.
- Валидировать так же, как классическая аннотация.
- Конвертировать один ТД в другой на этапе возвращения данных.
- Фильтровать данные.
________________________________________________________________________

Пример ситуации для конвертации: приходится собирать данные вручную в
словарь вместо специального объекта, а затем возвращать.

Если сделать классически, то редактор кода и инструменты могут ругаться
на возвращаемый ТД, т.к. он не соответствует указанному, и это
действительно является ошибкой. Но если сообщить в response_model, к
чему это надо привести, то данные автоматически преобразуются, что
решает проблему с инструментами, приведением результата в нужный вид и
автоматической валидацией.

Но это не решает проблему с редактором кода. Для временного решения
воспользуется `typing.Any`, что позволит редактору кода не ругаться, а
позднее восполним и утраченное удобство исп-я редакторов.

Наглядно:

```py
class Item(BaseModel):
    name: str,
    weight: float,
    tags: list[str] = []

fake_db: list[Item] = []

...

@app.get('/items/try-combine')  # без модели ответа
async def get_combine_res() -> Item:
    return {'name': ...,  # представим ф-цию получения результата
                          # объединения для каждого пар-ра отдельно
            'weight': ...,
            'tags': ['combined', ...]}  # инструменты и FastAPI ругаются

@app.get('/items/try-combine', response_model=Item)  # с моделью ответа
async def get_combine_res() -> Any:
    return {'name': ...,  # представим ф-цию получения результата
                          # объединения для каждого пар-ра отдельно
            'weight': ...,
            'tags': ['combined', ...]}  # претензий нет, в т.ч. от
                                        # редактора кода, т.к. объявлен
                                        # тип Any
```

Второй вариант приводит словарь в нужный вид модели Item, инструменты не
ругаются. Впрочем, такое можно сделать и вручную, создав отдельно объект
Item с полями, но запись через response_model может избавить от лишнего
кода.
________________________________________________________________________

Но куда важнее у response_model ф-ция фильтрации. Пример: надо вернуть
урезанный экземпляр к-л модели данных (пускай данные о к-л предмете).

Наглядно на примере оружия в вымышленной игре как предмета и как лота у
продавца:

```py
class Item(BaseModel):
    name: str,
    weight: float,
    description: str | None = None,
    price: int,
    category: int,
    tags: list[str] = [],
    img_id: int

class Weapon(Item):
    damage: int,
    speed: int,
    animation_ids: dict[str, int],
    spec_info: str,
    secret_info: str

class SellerLot(BaseModel):
    name: str,
    weight: float,
    description: str | None = None,
    price: int,
    category: int

class SellerLotWeapon(SellerLot):
    damage: int,
    speed: int
```

Как видно, пар-ров у предмета значительно больше, чем у лота продавца, в
том числе и какой-то информации, которая игроку не нужна.

Продолжим:

```py
# набор оружий
fake_seller_weapons_db = [
    Weapon(name='knife', ...),
    Weapon(name='bow', ...),
    ...
]

# вручную
@app.get('seller/weapons/{number}')
async def get_weapon_from_seller(number: int) -> SellerLotWeapon:
    weapon = fake_seller_weapons_db[number]
    return SellerLotWeapon(name=weapon.name,
                           weight=weapon.weight,
                           ...,
                           speed=weapon.speed)

# с response_model
@app.get('seller/weapons/{number}', response_model=SellerLotWeapon)
async def get_weapon_from_seller(number: int) -> Any:
    return fake_seller_weapons_db[number]
```

Как видно из примера, второй вариант меньше по кол-ву кода, что делает
его читаемее, а автоматическое приведение ТД при возвращении данных
затратит меньше ресурсов. Здесь и заложено основное преимущество
response_model - с таким объявлением FastAPI сам разберется, какие поля
нужны в ответе (выходной модели), а какие нет - и выкинет ненужное.
________________________________________________________________________

Но есть оставшаяся проблема - Any, объявляемый в случаях выше,
заставляет редактор кода и линтер не ругаться на ТД, но мы теряем в
удобстве (автодополнение, переходы через Ctrl и т.д.) и все еще
недостаточно хороша читаемость.

Решение этой проблемы заодно и позволит соблюсти принципы наследования и
абстракции в ООП. А именно исп-ть классы и механику наследования для
объединения.

Рассматривая предыдущий пример и сворачивая его только до предметов для
компактности:

```py
class AbstractItem(BaseModel):
    name: str,
    weight: float,
    description: str | None = None,
    price: int,
    category: int

class Item(AbstractItem):
    tags: list[str] = [],
    img_id: int,
    spec_info: str,
    secret_info: str

class SellerLot(AbstractItem):
    pass


# набор предметов
fake_seller_items_db = [
    Item(name='apple', ...),
    Item(name='ring', ...),
    ...
]


@app.get('seller/items/{number}', response_model=SellerLot)
async def get_item_from_seller(number: int) -> AbstractItem:
    return fake_seller_items_db[number]
```

Теперь редактор кода не ругается, т.к. Item - подкласс AbstractItem; и в
то же время стало читаемее, а исп-е результатов ф-ции подтянет и
автодополнение.
________________________________________________________________________

Полезные фишки:

- `response_model=None` - отключить модель ответа.

- В response_model можно исп-ть несколько ТД, но не как в аннотации
    типов, ибо это присваивание, а не аннотация, и Python попробует
    провести операцию `|` и выдаст ошибку. Правильно будет исп-ть
    `typing.Union[<type1>, <type2>, ...]`.

- Там же можно исп-ть и list, и set, уже как везде.

- Есть еще полезные пар-ры этой серии:

    - `response_model_exclude_unset=True` - опустить в ответе те пар-ры,
        которые не были установлены (например, значения по умолчанию,
        которые не были проставлены туда вручную).
    
    - `response_model_exclude_defaults=True` - опустить в ответе те
        пар-ры, которые равны значениям по умолчанию.
    
    - `response_model_exclude_none=True` - опустить в ответе пар-ры,
        равные None.
    
    - `response_model_include=<set_of_names>` - принимает мн-во с
        именами полей, которые нужно включить в ответ, исключая
        остальные. Позволяет сделать фильтрацию и без доп. классов, но
        в то же время мб неудобен и менее читаем, особенно если мн-во
        имен большое. Можно также вместо мн-ва исп-ть список или кортеж
        \- автоматически преобразуются в мн-во.
    
    - `response_model_exclude=<set_of_names>` - аналогично предыдущему,
        но мн-во с именами полей, которые нужно исключить из ответа,
        оставив все остальное.

- Если все-таки нужно сначала какие-то поля модели изменить - тогда,
    чтобы не присваивать все поля сразу, можно исп-ть метод `model_dump`
    для получения словаря с пар-рами и распаковку из Python при создании
    новой модели.

    На примере того же продавца предметов предположим, что он в зав-ти
    от своего отношения к игроку меняет цену на к-л коэффициент:

    ```py
    class AbstractItem(BaseModel):
        ...
        price: int,  # теперь это номинальная стоимость
        ...

    class Item(AbstractItem):
        ...

    class SellerLot(AbstractItem):
        sell_price: int  # новый параметр, отличающийся от номинальной
                         # стоимости, в данном случае стоимость продажи


    # набор предметов
    fake_seller_items_db = [...]

    # коэффициент продавца, отражающий скидку или наценку
    seller_coeff: float = ...


    @app.get('seller/items/{number}', response_model=SellerLot)
    async def get_item_from_seller(number: int) -> AbstractItem:
        item = fake_seller_items_db[number]
        sell_item = SellerLot(**item.model_dump(),
                              sell_price=int(seller_coeff * item.price))
        return sell_item
    ```

    > **ВАЖНО!** Нужно после этого сохранить наличие пар-ра
    response_model у декоратора операции пути, т.к. в sell_item будут
    находиться как новый пар-р sell_price, так и все пар-ры экземпляра
    Item, в т.ч. те, которых там быть не должно. Фильтрация за счет
    response_model решит данную проблему.
________________________________________________________________________

### ДРУГИЕ АННОТАЦИИ ОТВЕТА ###

В случаях, когда возвращается что-то, не являющееся валидным полем
Pydantic, но нужно иметь аннотацию для читабельности и поддержки
инструментов редактора кода, можно возвращать ответ напрямую с помощью
`fastapi.Response` и более конкретных `fastapi.responses.<some_resp>`,
которые являются подклассами fastapi.Response.

Для больших подробностей - см. документацию.

Некотрые из них:

- `RedirectResponse(url='some_url')` - перенаправление на some_url.
- `JSONResponse(content={...})` - ответ в формате JSON.
- `HTMLResponse(content='...')` - ответ в формате HTML для передачи
    веб-форм и страниц.
- `PlainTextResponse('<some_str>')` - ответ в формате чистого текста.
________________________________________________________________________

Пример:

```py
@app.get('/')
async def get_root() -> Response:
    if ...:
        return RedirectResponse(url=...)
    return JSONResponse(content={...})
```

Здесь не исп-ся response_model, т.к. ответ не является Pydantic моделью,
т.е. такого уровня валидации ждать не стоит, но базовая валидация
соответствия от FastAPI сохраняется. Кроме того, сохраняется и описанная
в "Модели ответа" аннотация и поддержка от редакторов кода ч/ исп-е
классов и подклассов.

> **ВАЖНО!** Нельзя возвращать т.о. что-то произвольное или миксовать с
валидными для Pydantic ТД или моделями ч/ `|` - это приведет к ошибке.
Поэтому в примере исп-ся JSONResponse, хотя выглядит так, будто можно
было вернуть все проще.
________________________________________________________________________

### СТАТУС-КОД ОТВЕТА ###

Кратко о статус-кодах:

- *1хх* - информационные, не имеют тела, редко исп-ся разработчиками
    напрямую.

- *2хх* - успешная обработка запроса, исп-ся чаще всего. Более
    конкретные примеры:
    - 200 (ОК) - стоит по умолчанию.
    - 201 (Created) - после создания записи в БД.
    - 204 (No Content) - нет содержимого для возврата, не имеет тела.

- *3хх* - перенаправление.
    - 304 (Not Modified) - не модифицирован, без тела ответа.

- *4хх* - ошибка со стороны клиента, еще одна наиболее часто исп-мая
    категория кодов. Примеры:
    - 400 - для общих ошибок.
    - 404 (Not Found) - не найдено.

- *5хх* - ошибка со стороны сервера. Почти никогда не исп-ся напрямую,
    обычно сервер сам возвращает в случае проблем в серверной части.
________________________________________________________________________

По аналогии с моделью ответа можно задать статус-код ответа по умолчанию
с помощью пар-ра `status_code` операции пути (get, post и др.). Данный
пар-р принимает число, представляющее код статуса HTTP-ответа.

Для того, чтобы не использовать чистое численное обозначение (для
читаемости и более простого понимания) можно исп-ть константы из
`fastapi.status`.

Пример:

```py
from fastapi import FastAPI, status

...

@app.post('/', status_code=status.HTTP_201_CREATED)
async def post_root(...):
    ...
```
________________________________________________________________________

В случае, если нужно сообщить клиенту об ошибке в ходе обработки
HTTP-запроса, ответа по умолчанию становится недостаточно. Для этого
вызывается исключение `fastapi.HTTPException` с указанием в пар-ре
`status_code` данного исключения статус-кода. Кроме того, можно указать
пар-р `detail` в формате str для деталей и словарь `headers` с
заголовками, но последний исп-ся редко.

Пример:

```py
fake_items_db = {...}

@app.get('/items/{item_id}')
async def get_item(item_id: str):
    if item_id not in fake_items_db:
        raise HTTPException(status_code=404
                            detail='Item not found')
    return {'item': fake_items_db[item_id]}
```

Такой формат вернет стандартный HTTP-ответ с указанным статус-кодом. Для
более специализированного ответа нужно исп-ть обработчик исключений,
чему посвящен подраздел "Обработка ошибок" данного конспекта.
________________________________________________________________________

Кроме того, пар-р status_code имеют и некоторые др. классы, которые
можно вернуть в качестве ответа, например, многие дочерние классы
Response (например, JSONResponse). Т.о. можно обозначить статус-код
ответа без прибегания к вызову исключения или передать статус-код более
точечно.
________________________________________________________________________

### ОБРАБОТКА ОШИБОК ###

Несмотря на возникающие ошибки, сервер FastAPI не падает при их
возникновении, т.к. у него есть обработчики исключений. Самый базовый
пример - возвращение JSON с деталями ошибки при непрохождении валидации
переданных данных.

Можно установить пользовательские обработчики исключений как для своих,
так и для библиотечных исключений. Делается это с помощью декоратора
`@app.exception_handler(<exc>)`, где exc - класс-исключение, которое
следует обрабатывать FastAPI. У ф-ции-обработчика должны иметься пар-ры,
принимающие в себя запрос в ТД `fastapi.Request` (или ином по необх-ти)
и исключение.
________________________________________________________________________

Пример обработчика кастомного исключения:

```py
class MyException(Exception):
    ...

@app.exception_handler(MyException)
async def my_exception_handler(request: Request, exc: MyException):
    ...
    return JSONResponse(status_code=400,
                        content={'message': 'My exception triggered'})
```
________________________________________________________________________

Со стандартными обработчиками исключений FastAPI нужно быть осторожнее:
т.к. FastAPI пользуется библиотекой Starlette для работы с
HTTP-запросами и ответами, есть дублирующиеся функционалии с разным
синтаксисом.

Например, HTTPException из FastAPI имеет более лояльный к передаваемым
ТД пар-р detail, в то время как HTTPException из Starlette принимает
только строки. Кроме того, при исп-ии из кода спокойно можно вызывать
FastAPI HTTPException, но "под капотом" исп-ся и вызывается именно что
исключение из Starlette. Поэтому при переобозначении обработчика нужно
подвязывать его именно к Starlette HTTPException, даже если из кода
триггерится онное из FastAPI. Т.о., если что-то из-под "капота" вызовет
HTTPException, оно обработается так же, как и при ручном вызове, а
именно переобозначенным новым обработчиком.

В то же время, например, исключение `RequestValidationError` из
`fastapi.exceptions`, отвечающее за невалидные данные, относится сугубо
к FastAPI.

Примеры:

```py
from fastapi import FastAPI, HTTPException
from fastapi.exceptions import RequestValidationError
from starlette.exceptions import HTTPException as StarletteHTTPException
# здесь добавили Starlette HTTPExceptions элиас для различения

...

# переобозначаем именно Starlette HTTPException
@app.exception_handler(StarletteHTTPException)
async def http_exc_handler(...):
    ...

# а тут уже FastAPI RequestValidationError
@app.exception_handler(RequestValidationError)
async def request_validation_error_handler(...)
    ...

...

# а здесь пример того, что несмотря на переобозначение обработчика для
# исключения из Starlette, это работает и для исключения из FastAPI
@app.get('/')
async def get_root(...):
    ...
    if ...:
        raise HTTPException(...)
    ...
```
________________________________________________________________________

Если вдруг понадобится расширить функционал стандартных обработчиков
исключений, задействуя их, то можно их подтянуть из
`fastapi.exception_handlers`. Это асинхронные ф-ции, их результат
следует получать ч/ `await`.
________________________________________________________________________

## ПОЛЕЗНЫЕ ФИЧИ ##

У операций пути (тех, которые описываются ч/ декоратор) можно исп-ть
некоторые пар-ры для аннотации и отображения в документации.

- `status_code` - описано ранее в "Ответы" -> "Статус-код ответа".

- `tags=<list[str]>` - добавить теги для группирования операций в
    документации. Имеет смысл завести класс, дочерний Enum, с
    тегами для более грамотного исп-я с минимумом риска опечатки и
    поддержкой редактора кода.

- `summary=<str>` - краткое описание.

- `description=<str>` - описание. Можно получить описание и из станд.
    строки документации ф-ции Python, поддерживается Markdown.

- `response_description=<str>` - описание ответа. Согласно OpenAPI
    описание ответа необходимо каждой операции пути.

- `depricated=True` - обозначение за устаревшее.
________________________________________________________________________

`jsonable_encoder` - ф-ция из `fastapi.encoders`, которая преобразует
объект (например, Pydantic-модель или дату-время) в совместимый с JSON
(на тех же примерах - в словарь и строку соотв.). Это может оказаться
крайне полезно при работе с БД.
________________________________________________________________________

Напоминание исп-ть PATCH-метод вместо PUT-метода при частичном
обновлении - для большего понимания, хотя в реальной практике часто про
PATCH забывают.

Тут же могут быть полезны:

- Метод `model_dump` и `model_copy` Pydantic-моделей.
- Пар-р `exclude_unset` метода `model_dump` - для игнорирования полей,
    не объявленных явно.
- Пар-р `update` метода `model_copy` - для обновления данных в модели с
    использованием другой модели.

Все это мб нужно, чтобы не было проблем при копировании и изменении
данных, чтобы не записать значения по умолчанию вместо уже сохраненных
данных при неуказании новшеств, чтобы не было проблем при неуказании
обязательных данных и т.п.

Пример исп-я метода PATCH:

```py
fake_db: dict[str, dict] = ...

@app.patch('/items/{item_id}')
async def patch_item(item_id: str, item: Item) -> Response:
    stored_item = fake_db[item_id]
    stored_item_model = Item(**stored_item)
    update_data = item.model_dump(exclude_unset=True)
    updated_item = stored_item_model.model_copy(update=update_data)
    fake_db[item_id] = jsonable_encoder(updated_item)
    return ...
```

## БЕЗОПАСНОСТЬ ##

Тема безоп-ти неотрывно связана с темой авторизации и аутентификации,
поэтому в данной части конспекта рассматривается именно в таком ключе.

Тема сложная и затронет большинство рассмотренных выше тем. Следует
изучить их прежде, чем приступать к изучению безоп-ти в контексте
FastAPI.

В качестве введения рассмотрим основные спецификации:

- *OAuth2* - обширная спецификация, определяющая различные способы
    обработки аут-ции и ав-ции, в т.ч. те способы, что подразумевают
    третью сторону ("войти с помощью Google" и проч.). Является как
    основной спецификацией в контексте данной темы, так и основой для
    др. спецификаций.

- *OpedID Connect* - расширение для OAuth2 в сторону совместимости с
    третьей стороной (например, Google исп-т не OAuth2, а OpedID
    Connect).

- *OpenAPI* - открытая спецификация для создания API, на которой и
    основан FastAPI. В OpenAPI есть несколько схем безоп-ти, основанных
    на других спецификациях, которыми можно восп-ся:

    - *apiKey* - API-ключ, поступающий из пар-ра запроса, HTTP-заголовка
        или в качестве куки.
    
    - *http* - набор станд. систем аут-ции по HTTP, включая:
        - *bearer* - HTTP-заголовок `Authorization` со значением
            `"Bearer <token>"`, унаследованный от OAuth2.
        - Базовая аут-ция по HTTP.
        - HTTP Digest.
        - Др.
    
    - *oauth2* - как понятно, OAuth2. Содержит несколько способов
        (т.н. "потоков") аут-ции третьим лицом, но основное в контексте
        коспекта - аут-ция непосредственно в приложении с исп-ем
        "потока" `password`.
    
    - *openIdConnect* - как понятно, OpenID Connect.

Для каждой из схем безоп-ти есть инструменты в модуле
`fastapi.security`.
________________________________________________________________________

Кроме того, рассмотрим важные понятия:

- *Токен* - строка с некоторым содержимым, исп-емая для проверки
    пользователя. Обычно у токена установлен срок действия, после
    которого он недействителен.

- *Эмитирование* токена = выдача токена.

- *Хеширование* (в контексте темы) - одностороннее однозначное
    преобразование данных в строку с набором символов. Это означает, что
    для одних и тех же данных при разных вызовах хеш-ф-ции будет один и
    тот же результат, но при этом полученный хеш обратно в данные
    восстановить нельзя.

    В общем контексте хеширование имеет более широкое определение, без
    требований одностороннего преобразования. Кроме того, и в пределах
    данного контекста одностороннесть - идеалистическая концепция, в то
    время как теоретически расшифровать можно любой захешированный набор
    данных. Вопрос только во времени, однозначности обратного
    преобразования и, для простых методов, наличии исходного кода
    хеш-ф-ции.
________________________________________________________________________

### ПРОСТЕЙШАЯ СХЕМА ###

Простейшая схема подразумевает аут-цию по имени пользователя и паролю.

Ее вид:

```py
from typing import Annotated

from fastapi import Depends, FastAPI
from fastapi.security import OAuth2PasswordBearer

app = FastAPI()

oauth2_scheme = OAuth2PasswordBearer(tokenUrl='token')


@app.get('/')
async def get_root(token: Annotated[str, Depends(oauth2_scheme)]):
    return {'token': token}
```
________________________________________________________________________

Разберем ее функционал. Это аут-ция посредством *"password flow"* -
одного из способов обеспечения безоп-ти и аут-ции, определенных в
OAuth2. При этом тип токена - Bearer. За этот способ и тип токена
отвечает класс `OAuth2PasswordBearer`.

Идея следующая:

- В бэкенд передаются логин `username` и пароль `password`, введенные
    во фротненде, на конкретный эндпоинт. Этот эндпоинт описан в пар-ре
    `tokenUrl` класса OAuth2PasswordBearer. В данном случае -
    "./token" (относительный адрес). При этом сам эндпоинт или операция
    пути не создаются в таком объявлении - адрес отвечает чисто за
    получение токена. Для прочих обработок - придется создать эндпоинт
    отдельно.

- API проверяет пользователя и отвечает токеном, чтобы фронтенд его
    сохранил г-л. В примере выше этого еще нет.

- При последующем серфинге по сервису фронтенд отправляет для ав-ции не
    логин и пароль, а HTTP-заголовок `Authorization` со значением
    `"Bearer <token>"`.

Как видно из кода, за то, чтобы это работало, исп-ся переменная
oauth2_scheme. Она содержит в себе вызываемый объект - экземпляр класса
OAuth2PasswordBearer. Этот экземпляр надо передать как зав-ть, и она
пердоставит токен в формате str - поэтому пар-р операции пути описан
именно так.

Под капотом эта зав-ть делает следующее:

- Ищет заголовок Authorization и проверяет его на соответствие виду
    `"Bearer <token>"`.

- Если заголовка нет или вид его не соответствует - отвечает ошибкой со
    статус-кодом 401 Unauthorized.

Проверка валидности токена (которой пока что нет) возлагается на код
разработчика.
________________________________________________________________________

### ПОЛУЧЕНИЕ ТЕКУЩЕГО ПОЛЬЗОВАТЕЛЯ ###

Исп-е зав-ти с безоп-тью в таком виде не особо полезно, ведь возвращение
и чистое исп-е токена в пределах бэкенда редко нужно. Вместо этого
добавим базовую работу с пользователем и его получение.

Для олицетворения пользователя восп-ся моделями Pydantic.

```py
from typing import Annotated

from fastapi import Depends, FastAPI
from fastapi.security import OAuth2PasswordBearer
from pydantic import BaseModel

app = FastAPI()

oauth2_scheme = OAuth2PasswordBearer(tokenUrl='token')


class User(BaseModel):
    username: str,
    email: str | None = None
    full_name: str | None = None


def fake_user_getter(token: str):
    return User(
        username=token + '_fake_got',
        email=token + '_fake_email@example.com',
        full_name='Ivan Ivanov'
    )

async def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]):
    return fake_user_getter(token)


@app.get('/')
async def get_root(current_user: Annotated[User, Depends(get_current_user)]):
    return current_user
```
________________________________________________________________________

В коде добавилось:

- Описание пользователя как Pydantic-модели User.
- Фейковый геттер пользователя fake_user_getter - в реальном проекте
    будет получение из БД, но в данном случае это чистая заплашка.
- Зав-ть get_current_user, возвращающая пользователя. Она заместила
    зав-ть oauth2_scheme в операции пути, но сама при этом стала
    зависеть от oauth2_scheme - вложенные зав-ти.

Теперь этот код в первую очередь достиг того, что разделил безоп-ть от
основного кода - операции пути. get_root теперь работает чисто с
пользователем, а безоп-тью занимается неотделимый от нее геттер текущего
пользователя. В реальном проекте можно и нужно будет раскидать это по
разным скриптам.

Кроме того, постепенно внедряем в сухой скелет нужные и полезные вещи и
практики. Это предварительный этап перед полным "потоком" безопасности.
________________________________________________________________________

### OAUTH2 С ПАРОЛЕМ + BEARER ###

Теперь введем полный "поток" безоп-ти в простом виде. Сначала приведем
код, а затем рассмотрим все нововведения.

```py
from typing import Annotated

from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from pydantic import BaseModel


fake_users_db = {
    'ivanivan': {
        'username': 'ivanivan',
        'full_name': 'Ivan Ivanov',
        'email': 'ivanivan@example.com',
        'hashed_password': 'fakehashedivansecret',
        'disabled': False
    },
    'petya': {
        'username': 'petya',
        'full_name': 'Pyotr Petrov',
        'email': 'petyapetya@example.com',
        'hashed_password': 'fakehashedpetyasecret',
        'disabled': True
    }
}

app = FastAPI()

oauth2_scheme = OAuth2PasswordBearer(tokenUrl='token')


class User(BaseModel):
    username: str,
    email: str | None = None
    full_name: str | None = None
    disabled: bool | None = None


class UserInDB(User):
    hashed_password: str


def fake_hash_password(password: str):
    return 'fakehashed' + password

def get_user(db, username: str):
    if username in db:
        user_dict = db[username]
        return UserInDB(**user_dict)

def fake_decode_token(token):
    user = get_user(fake_user_db, token)
    return user


async def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]):
    user = fake_decode_token(token)
    if not user:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail='Not authenticated',
            header={'WWW-Authenticate': 'Bearer'}
        )
    return user

async def get_current_active_user(
    current_user: Annotated[User, Depends(get_current_user)] 
):
    if current_user.disabled:
        raise HTTPException(status_code=400, detail='Inactive user')
    return current_user


@app.post('/token')
async def login(form_data: Annotated[OAuth2PasswordRequestForm, Depends()]):
    user_dict = fake_users_db.get(from_data.username)
    if not user_dict:
        raise HTTPException(status_code=400, detail='Incorrect username or password')
    user = UserInDB(**user_dict)
    hashed_password = fake_hash_password(form_data.password)
    if not hashed_password == user.hashed_password:
        raise HTTPException(status_code=400, detail='Incorrect username or password')
    return {'access_token': user.username, 'token_type': 'bearer'}

@app.get('/')
async def get_root(
    current_user: Annotated[User, Depends(get_current_active_user)]
):
    return current_user
```
________________________________________________________________________

Для начала рассмотрим вспомогательные вещи:

- Пока что мы не работаем с реальным токеном, а в качестве токена исп-ем
    username для простоты (хотя это мб несколько запутывающе). Очевидно,
    так делать в реальном проекте нельзя.

- User обзавелся новым полем disabled для хранения флага "отключенности"
    (активности) пользователя. При этом появился дочерний UserInDB,
    который содержит еще одно поле hashed_password - захешированный
    пароль.
    
    > **ВАЖНО!** В открытом виде хранить пароли небезопасно! Хранить
    надо именно хешированный пароль! Это нужно, чтобы в случае угона БД
    с пользователями нельзя было всопользоваться паролями.

- fake_users_db - фейковая БД пользователей в формате словаря со
    словарями вида dict[имя-пользователя, dict[поле, значение]].
    Структура полей согласуется с UserInDB (точнее, наоборот, UserInDB
    написан так, чтобы согласоваться со структурой полей в БД). Записаны
    они в виде словаря словарей для имитации реальной БД со своим
    интерфейсом.

- fake_hash_password - фейковая ф-ция хеширования паролей. В реальном
    проекте заменяется на реальное хеширование.

- get_user - ф-ция для получения пользователя из БД.

- fake_decode_token - фейковая ф-ция для декодирования токена в
    пользователя. В данном случае - ф-ция-прослойка без предоставления
    к-л безоп-ти. В реальном проекте так не делается.
________________________________________________________________________

Теперь рассмотрим операцию пути login.

- Пар-р form_data принимает в себя данные формы. В данном случае ТД
    объявлен как `OAuth2PasswordRequestForm` - специальный зав-ть-класс,
    дочерний Form, представляющий собой форму под OAuth2 аут-цию с
    паролем. На самом деле не представляет из себя ничего необычного и
    мб написан вручную, но дан в FastAPI для упрощения.
    
    Содержит в себе поля:

    - `username` - обязательное поле.
    - `password` - обязательное поле.
    - `scope` - необязательное поле в виде большой строки отдельных
        scope, разделенных пробелом (обсудим отдельно). При этом у
        экземпляра OAuth2PasswordRequestForm будет не одна строка, а
        атрибут `scopes`, содержащий список строк. Нужен для добавления
        определенных разрешений и ограничений.
    - `grant_type` - необязательное для OAuth2PasswordRequestForm поле,
        но вообще для спецификации OAuth2 поле обязательно и должно
        содержать фиксированное значение password. Если прям необходимо
        строгое стребование, исп-ть OAuth2PasswordRequestFormStrict.
    - `client_id` - необязательное поле.
    - `client_secret` - необязательное поле.

    В нашем примере исп-ся только поля username и password.

- Первым делом получаются данные о пользователе из фейковой БД с помощью
    поля username из данных формы. Если пользователя нет - вызывается
    ошибка 400 'Incorrect username or password'. Если есть - собирается
    экземпляр UserInDB для дальнейшей работы.

- Проверка пароля производится через сравнение хеша от password из
    данных формы и хешированного пароля в БД. Если не равны - вызывается
    ошибка 400 'Incorrect username or password'.

- Если проверки все прошли успешно - возвращается специализированный
    ответ формата JSON с обязательными полями:

    - `access_token` - строка с токеном доступа.
    - `token_type` - строка с типом токена, в нашем случае - "bearer".

Итого вся эта операция пути предназначена для произведения логина и
выдачи токена авторизировавшему пользователю.
________________________________________________________________________

Перейдем к get_root:

- Появилась проверка активности пользователя. Теперь get_root имеет
    зав-ть от get_current_active_user, который имеет зав-ть от
    get_current_user, который имеет зав-ть от oauth2_scheme.

    get_current_active_user в этом плане зав-ть-прослойка для проверки
    активности пользователя, полученного от get_current_user.

    Если пользователь не активен, то вернется ошибка с сообщением о
    неактивности пользователя.

- get_current_user претерпел изменения как чтобы брать пользователя из
    новой фейковой БД, так и чтобы возвращать ошибку в случае, если
    пользователя нет.

    Он задействует фейковый декодер токена, который, в свою очередь, и
    должен по токену отыскать пользователя.

    Кроме того, возвращаемая ошибка в случае ненайденного пользователя
    имеет специальный вид:
    
    - Ошибка имеет статус-код 401.
    - Заголовок `WWW-Authenticate` является частью спецификации - ошибка
        с кодом 401 обязана возвращать такой. Работать все будет и без
        заголовка, но спецификация требует его наличие, а ряд
        инструментов может ожидать и исп-ть этот заголовок.
    - В нашем случае с bearer-токеном этот заголовок должен содержать
        значение `Bearer`.
________________________________________________________________________

### ХЕШИРОВАНИЕ И JWT ###

Наконец, можно перейти к окончательным доработкам в безоп-ти:
правильному хешированию и действительным токенам.

Самый ходовой стандарт для токенов - *JWT*, или JSON Web Tokens. Это
стандарт кодирования JSON-объекта в виде длинной строки без пробелов.
Есть зашифрованная подпись, что именно данный сервис его эмитировал.

Т.о. можно создать токен со сроком действия, заложенном в нем, а если
его попробуют модифицировать - его выдаст другая подпись.

JWT в расшифрованном виде содержит в себе заголовок с алгоритмом
кодирования и типом ("JWT"), тело (т.н. "payload") с данными (их должно
быть немного, обычно лишь "sub" с субъектом токена наподобие имени
пользователя, его роль в к-л формате и время истечения "exp") и подпись
на основании соли в зашифрованном виде.

Побаловаться с JWT: см. "Источники и доп. материалы".
________________________________________________________________________

Для работы с JWT-токенами понадобится библиотека `pyjwt`. Если нужны
алгоритмы цифровой подписи - следует установить зав-ть библиотеки
криптографии с помощью указания издания `pyjwt[crypto]`.

Для хеширования отличным пакетом будет `pwdlib`. Мн-во безопасных
алгоритмов хеширования и утилит для работы с ними. Авторы туториала
рекомендуют алгоритм Argon2, а также упоминают Bcrypt.

В специфическом случае может понадобиться библиотека `passlib` для более
устаревших алгоритмов хеширования, т.к. pwdlib таковые не поддерживает.
________________________________________________________________________

Теперь конечный код:

```py
from datetime import datetime, timedelta, timezone
from typing import Annotated

import jwt
from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from jwt.exceptions import InvalidTokenError
from pwdlib import PasswordHash
from pydantic import BaseModel


SECRET_KEY = '...'  # какой-то случайный hex 32 ключ
ALORITHM = 'HS256'
ACCESS_TOKEN_EXPIRE_MINUTES = 30


fake_users_db = {
    'ivanivan': {
        'username': 'ivanivan',
        'full_name': 'Ivan Ivanov',
        'email': 'ivanivan@example.com',
        'hashed_password': ...,  # какой-то хешированный пароль
        'disabled': False
    },
    'petya': {
        'username': 'petya',
        'full_name': 'Pyotr Petrov',
        'email': 'petyapetya@example.com',
        'hashed_password': ..., # какой-то хешированный пароль
        'disabled': True
    }
}

password_hash = PasswordHash.recommended()

DUMMY_HASH = password_hash.hash('some_dummy_password')

app = FastAPI()

oauth2_scheme = OAuth2PasswordBearer(tokenUrl='token')


class Token(BaseModel):
    access_token: str
    token_type: str


class TokenData(BaseModel):
    username: str | None = None


class User(BaseModel):
    username: str,
    email: str | None = None
    full_name: str | None = None
    disabled: bool | None = None


class UserInDB(User):
    hashed_password: str


def verify_password(plain_password, hashed_password):
    return password_hash.verify(plain_password, hashed_password)

def get_password_hash(password):
    return password_hash.hash(password)

def get_user(db, username: str):
    if username in db:
        user_dict = db[username]
        return UserInDB(**user_dict)

def authenticate_user(db, username: str, password: str):
    user = get_user(db, username)
    if not user:
        verify_password(password, DUMMY_HASH)
        return False
    if not verify_password(password, user.hashed_password):
        return False
    return user

def create_access_token(data: dict, expires_delta: timedelta | None = None):
    to_encode = data.copy()
    if expires_delta:
        expire = datetime.now(timezone.utc) + expires_delta
    else:
        expire = datetime.now(timezone.utc) + timedelta(minutes=15)
    to_encode.update({'exp': expire})
    encoded_jwt = jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)
    return encoded_jwt


async def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]):
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail='Could not validate credentials',
        headers={'WWW-Authenticate': 'Bearer'}
    )
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        username = payload.get('sub')
        if username is None:
            raise credentials_exception
        token_data = TokenData(username=username)
    except InvalidTokenError:
        raise credentials_exception
    user = get_user(fake_users_db, username=token_data.username)
    if user is None:
        raise credentials_exception
    return user

async def get_current_active_user(
    current_user: Annotated[User, Depends(get_current_user)] 
):
    if current_user.disabled:
        raise HTTPException(status_code=400, detail='Inactive user')
    return current_user


@app.post('/token')
async def login_for_access_token(
    form_data: Annotated[OAuth2PasswordRequestForm, Depends()]
) -> Token:
    user = authenticate_user(fake_users_db, form_data.username, form_data.password)
    if not user:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail='Incorrect username or password',
            headers={'WWW-Authenticate': 'Bearer'}
        )
    access_token_expires = timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    access_token = create_access_token(
        data={'sub', user.username}, expires_delta=access_token_expires
    )
    return Token(access_token=access_token, token_type='bearer')

@app.get('/')
async def get_root(
    current_user: Annotated[User, Depends(get_current_active_user)]
):
    return current_user
```
________________________________________________________________________

Для начала рассмотрим вспомогательные вещи:

- Константы:

    - *SECRET_KEY* - секретный ключ для подписи JWT-токенов (т.н.
        "соль"). Можно исп-ть команду в терминале `openssl rand -hex 32`
        для получения такового.

        > **ВАЖНО!** Не стоит его хранить вот так в переменной. Лучше
        хранить ключ в отдельном файле, причем при работе с git закинуть
        этот файл в исключения для избежания утечек. Кроме того, этот
        файл должен быть хорошо защищен от злоумышленников.

    - *ALGORITHM* - строковая переменная с названием алгоритма для
        подписи JWT-токена. Рекомендуемый алгоритм - HS256.

    - *ACCESS_TOKEN_EXPIRE_MINUTES* - время истечения токена в минутах.

    - *DUMMY_HASH* - фиктивный хеш-пустышка, который создается от
        пароля-пустышки. Он исп-ся в authenticate_user для того, чтобы
        в случае вызова с именем пользователя, которого нет в БД, сервер
        отвечал столько же времени, как будто такой пользователь есть.
        Нужно для контрмер тайминговым атакам по поиску действительных
        имен пользователей.

- password_hash - сущность с функционалом для работы с хешем. Исп-ся
    методы `hash` для получения хеша и `verify` для сравнения чистых
    данных и захешированных с возвратом bool.

    Сама сущность создается методом класса `PasswordHash`, в данном
    случае исп-ся рекомендованный алгоритм Argon2.

- Для удобства появились модель для токена и данных из декодированного
    токена Token и TokenData соотв.

- verify_password - ф-ция для удобства сверки полученного чистого пароля
    и хешированного.

- get_password_hash - ф-ция для удоства хеширования пароля.

- authenticate_user - аут-ция пользователя по логину и паролю с учетом
    нового хеширования.

- create_access_token - вспомогательная ф-ция для создания токена.
    Принимает в себя данные для шифрования и время истечения токена в
    формате datetime.timedelta. Все это кодируется с помощью
    `jwt.encode(данные, соль, algorithm=алгоритм)`.
________________________________________________________________________

Основные методы претерпели изменения согласно вспомогательным:

- get_current_user - теперь действует не с фейковым токеном, а с JWT,
    декодируя его с помощью `jwt.decode` и проверяя данные в нем (в
    данном случае - по ключу "sub" хранится имя пользователя). Если
    токен по к-л причине недействителен - возвращает ошибку.

- get_current_active_user не изменился.

- login_for_access_token - обновленная операция пути "/token" с
    созданием реального JWT-токена с помощью create_access_token.
    Данные для создания JWT-токена предлагаются как {"sub": username}.
    Для более больших и разноплановых приложений можно исп-ть и другие
    поля для разграничений или указать доп. данные в строке по ключу
    "sub" ч/ разделитель. Важно, чтобы "sub" был уникален по всему
    приложению согласно спецификации, поэтому второй вариант (ч/
    разделитель) очень хорошо сходится с этим.

- get_root не изменился.

## MIDDLEWARE-ФУНКЦИОНАЛ ##

### MIDDLEWARE ###

*Middleware* (промежуточный слой) - это ф-ция, которая выполняется с
каждым запросом до его обработки операцией пути и перед каждым ответом
до его возвращения.

Данный функционал является основой для некоторых важных механизмов в
FastAPI, описанных в данном подразделе.

Пос-ть:

- Принимает каждый поступающий запроса.
- Делает ч-л.
- Передает запрос в операцию пути.
- Получает ответ от операции пути.
- Делает ч-л.
- Возвращает ответ.
- (Опционально при наличии yield-зав-тей) Выполняется код выхода
    yield-зав-тей.
________________________________________________________________________

Задается с помощью декоратора `@app.middleware('http')`, при этом ф-ция
должна иметь:

- Пар-р request ТД Request, принимающий запрос.
- Пар-р call_next, куда попадает ф-ция, принимающая запрос, передающая
    его нужной операции пути и возвращающая ответ этой операции. Внутри
    middleware-ф-ции должен быть вызов call_next ч/ await для передачи
    запроса и последующего получения ответа.

Пример:

```py
@app.middleware('http')
async def some_func(request: Request, call_next):
    ...  # к-л действия перед передачей в операцию пути
    response = await call_next(request)
    ...  # к-л действия перед возвратом ответа
    return response
```

Есть и другой синтаксис: объявить middleware-ф-цию без декоратора, а
затем исп-ть метод `app.add_middleware(<func>)` для добавления.
________________________________________________________________________

Порядок выполнения middleware-ф-ций определяется их порядком объявления:
каждая следующая ф-ция оборачивает уже имеющуюся структуру обработки,
т.е. первая объявленная выполнится при запросе последней, но первая
вернет ответ.
________________________________________________________________________

### CORS ###

*CORS* (Cross-Origin Resource Sharing) - когда запущенный в браузере
фронтенд содержит JS-код, который взаимодействует с бэкендом на другом
"источнике". "Источник" тут - это набор протокола, адреса и порта,
поэтому даже в пределах локала многие вещи находятся на разных
"источниках".

Проявляется это следующими шагами:

- Фронтенд ч/ JS-код пытается сделать запрос до бэкенда.
- Этот запрос останавливается браузером, и браузер отправляет
    OPTIONS-запрос бэкенду на разрешение.
- Если бэкенд отвечает HTTP-заголовками, авторизующими это подключение,
    то браузер разрешит JS отправить исходный запрос.

Вообще же это работает в целом с различными другими "источниками", не
только JS-кодом бэкенда. Это может быть и вообще другой сервис, и
HTTP-запрос из другого "источника". Для контроля доступа из других
"источников" и предназначен CORS. Подробнее о CORS - см. "Источники и
доп. материалы".

Для работы с CORS нужно, чтобы на бэкенде был список разрешенных
"источников", методов, заголовков и ряд доп. настроек.
________________________________________________________________________

В FastAPI это регулируется с помощью класса `CORSMiddleware`.

Принимает пар-ры:

- `allow_origins` - список "источников" в виде строк (с протоколом,
    доменом/адресом и портом в виде URL), по умолчанию - пустой список.
    Может принимать значение `['*']`, что позволяет любым "источникам"
    делать запросы, но сильно ограничивает дозволенные HTTP-методы,
    полностью запрещая любые учетные данные.
- `allow_origin_regex` - регулярное выражение для источников
    (опционально).
- `allow_credentials` - булево значение, позволяющее или запрещающее
    использование учетных данных (особые заголовки, куки и проч.). По
    умолчанию - False. По спецификации в остальных пар-рах при значении
    True не должно содержаться значения `['*']`, все должно быть указано
    явно.
- `allow_methods` - список разрешенных HTTP-методов в виде строк. Также
    может принимать значение `['*']`. По умолчанию - `['GET']`.
- `allow_headers` - список разрешенных заголовков. Также может принимать
    значение `['*']`. По умолчанию - пустой список. При этом заголовки
    "Accept", "Accept-Language", "Content-Language" и "Content-Type"
    всегда разрешены для простых CORS-запросов.
- `expose_headers` - список из заголовков ответа, которые должны быть
    доступны браузеру. По умолчанию - пустой список.
- `max_age` - максимальное время в секундах, в течение которого браузер
    кэширует CORS-ответы. По умолчанию - 600.

CORSMiddleware встраивается как middleware.

Пример:

```py
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

origins = [
    "...",
    "...",
    ...
]

app.add_middleware(
    CORSMiddleware,
    allow_origins=origins,
    allow_credentials=True,
    allow_methods=['*'],
    allow_headers=['*']
)

...
```
________________________________________________________________________

CORSMiddleware отвечает на 2 типа запросов:

- CORS-запросы с предварительной проверкой ч/ OPTIONS-запрос с
    заголовками "Origin" и "Access-Control-Request-Method". Тогда
    middleware перехватит входящий запрос и отправит соотв.
    CORS-заголовки в ответе + ответ со статус-кодом 200 или 400 в
    информационных целях.

- Простые запросы с заголовком "Origin". Тут middleware передаст запрос
    дальше для работы с ними как обычно, но на жтапе формирования и
    возврата ответа добавит к последнему CORS-заголовки.
________________________________________________________________________

## РАЗДЕЛЕНИЕ ОБЯЗАННОСТЕЙ ##

### МОДУЛИ И РОУТЕРЫ ###

Если нужно разделить ответственность за отдельные функциональности с
помощью модулей и файлов (в т.ч. в случае, когда в будущем может
понадобиться к-л отдельный набор ф-ций в другом проекте), но при этом
это должно быть все еще единое монолитное приложение, то FastAPI на этот
случай предоставляет API-роутеры.

На самом деле этот вопрос ("а как все грамотно разбить и разложить?") у
разработчика с ООП-мышлением и привычкой раскидывать все по отдельным
папкам и скриптам возникнет быстро.

В этом и помогут API-роутеры `fastapi.APIRouter`.

Синтаксис у них почти тот же, что и класса fastapi.FastAPI. Со стороны
синтаксиса API-роутеры - такие же приложения, как и основное. Авторы
оф. туториала позволяют исп-ть выражение "мини-класс FastAPI", хотя по
сути это не так. Роутеры - это лишь доп. инструкции основному приложению
FastAPI, набор своих настроек, зав-тей и операций пути. И весь этот
набор просто-напросто встраивается в основное приложение, будто все это
было там внутри изначально, а не лежало отдельно.

По сути все "как дома": роутер лишь маршрутизатор и не более того. А
если рассмотреть более технично, при добавлении роутера к основному
приложению просто происходит копирование (с учетом настроек) всех
операций пути роутера.

Поэтому такое приложение на FastAPI остается единым и монолитным, а все
операции пути и прочие настройки из APIRouter попадет в автоматическую
документацию. Кроме того, это не замедляет работу сервиса, только лишь
требует небольшого доп. времени при запуске для сборки воедино.
________________________________________________________________________

Постепенно рассмотрим функционал API-роутеров на примере.

Структура проекта:

```
.
|
+-- app
|   |
|   +-- __init__.py
|   +-- main.py
|   +-- dependencies.py
|   +-- routers
|   |   |
|   |   +-- __init__.py
|   |   +-- items.py
|   |   +-- users.py
|   |
|   +-- internal
|   |   |
|   |   +-- __init__.py
|   |   +-- admin.py
```

И в этом проекте мы хотим разделить обязанности по роутерам в
"app/routers/items.py" (для сокращения - items), "app/routers/users.py"
(users) и "app/internal/admin.py" (admin).
________________________________________________________________________

Допустим, users не зависит от остальных скриптов. Тогда мы можем сделать
так:

```py
from fastapi import APIRouter

router = APIRouter()


@router.get('/users/', tags=['users'])
async def get_users(...):
    ...

@router.get('/users/me', tags=['users'])
async def get_user_me(...):
    ...
```

Как видно, синтаксис абсолютно схож с классом fastapi.FastAPI.
________________________________________________________________________

В таком виде это полезно лишь разделением. Кроме того, видим повторения
и отсутствие обещанных настроек API-роутера. Да и предположение о том,
что не будет зав-тей при работе с пользователями крайне сомнительно.
Исправим это.

APIRouter принимает в себя следующие пар-ры:

- `prefix` - префикс для операций пути. Он "вкладывается" ровно между
    основным адресом (домен/IP) и остальным путем для операции. В
    примере выше можно вынести "/users" в префикс для меньших
    повторений.

- `tags` - список тегов для документации, общих для всех операций. В это
    же время к-л отдельные операции могут иметь свои доп. теги, но в
    итоге они для этих операций будут совокупностью тегов личных и тегов
    общих из пар-ра tags.

- `dependencies` - список зав-тей, которые должны быть применены ко всем
    операциям пути. По аналогии с тегами - мб личные зав-ти.

- `responses` - словарь с описанием ответов с ключом - кодом-статусом и
    значением - JSON-описанием. Для документации. Мб личные зав-ти.

Собственно, пар-ры также очень похожи на пар-ры класса FastAPI.

Вспомная о том, что к-н зав-ти нам точно понадобятся (предположим их
наличие в "app/dependencies.py"), и улучшая предыдущий пример:

```py
from fastapi import APIRouter, Depends

from ..dependencies import some_users_dep  # относительный импорт

router = APIRouter(
    prefix="/users",
    tags=["users"],
    dependencies=[Depends(some_users_dep)]
)


@router.get('/')  # как видно, префикс вынесся, как и теги
async def get_users(...):
    ...

@router.get('/me')
async def get_user_me(...):
    ...
```

Притом функционал (помимо добавления зав-ти) остался прежним.
________________________________________________________________________

Предположим, что мы примерно так же построили роутер в items. А вот
роутер в admin построили без настроек при объявлении экземпляра класса
APIRouter, перенеся admin из другого проекта, но требуется добавить
настройки на месте без переписывания этого скрипта.

Теперь с такими вводными рассмотрим "app/main.py". Это будет главной
точкой входа с главным приложением FastAPI. И для добавления в это
приложение роутеров достаточно исп-ть метод экземпляра `include_router`,
которому первым пар-ром сообщается экземпляр роутера, а далее именованно
можно передать настройки (как мы и хотели для admin).

Код:

```py
from fastapi import Depends, FastAPI

from .dependencies import some_admin_dep, some_main_dep
from .internal import admin
from .routers import items, users

app = FastAPI(dependencies=[Depends(some_main_dep)])


app.include_router(users.router)
app.include_router(items.router)
app.include_router(
    admin.router,
    prefix='/admin',
    tags=['admin'],
    dependencies=[Depends(some_admin_dep)],
    responses={418: {'description': 'I\'m an admin teapot'}}
)


@app.get('/')  # и к самому приложению все еще можно добавлять операции пути
async def get_root(...):
    ...
```

Вот и весь пример.
________________________________________________________________________

Теперь о полезных фичах:

- Для того, чтобы команда `fastapi` при запуске в консоли смогла сама
    найти точку входа, ее следует указать в спец. файле `pyproject.toml`
    следующим образом (на примере выше):

    ```
    [tool.fastapi]
    entrypoint = "app.main:app"
    ```

    Это эквивалентно импорту `from app.main import app`. Т.о. команда
    fastapi в терминале (и некоторые инструменты) смогут без проблем
    найти точку входа без необх-ти ее точного указания.

- Редко, но может понадобиться подключение одного и того же роутера под
    разные префиксы и теги (например, при сравнении версий). Как видно,
    такое возможно.

- Можно вкладывать роутеры, подключая один API-роутер к другому,
    который, в свою очередь, подключать уже к основному приложению.
________________________________________________________________________

### ПОДПРИЛОЖЕНИЯ И МОНТИРОВАНИЕ ###

Если нужно исп-ть два независимых приложения FastAPI, каждое со своей
документацией и функционалом, то можно исп-ть монтирование одного
приложения как подприложения другого.

Они полностью независимы, но при этом этот способ все еще не относится к
микросервисной архитектуре в ее полноценном виде.

Монтирование производится с помощью метода `mount(<prefix>, <subapp>)`
экземпляра класса FastAPI, где prefix - префикс, по которому будет
доступно API подприложения, а subapp - само подприложение (также
экземпляр класса FastAPI).
________________________________________________________________________

Пример:

```py
app = FastAPI()

@app.get('/some/endpoint')
async def get_some_endpoint():
    ...


subapi = FastAPI()

@subapi.get('/some/endpoint')
async def subapi_get_some_endpoint():
    ...


app.mount('/subapi', subapi)
```

В данном примере app - основное приложение, subapi - подприложение. При
этом подприложение занимает префикс "/subapi", т.е. путь
"./some/endpoint" обработается основным приложением, а путь
"./subapi/some/endpoint" - подприложением. Документации также раздельны:
у основного приложения будет один эндпоинт и у подприложения, а для
доступа нужно исп-ть "./docs" и "./subapi/docs" соотв.

При этом сохраняется единый основной адрес (домен, IP или localhost), но
приложения независимы, а для их общения понадобится производить
обращение ч/ честные HTTP-запросы (например, посредством `httpx`).

Кроме того, важно уточнить, что допускается вложенность, и у subapi мб
и свои подприложения. В таком случае FastAPI позаботится, чтобы все
работало так, как нужно, со всеми префиксами.
________________________________________________________________________

На самом деле монтирование также позволяет пользовать ASGI-шный FastAPI
с WSGI-шными Flask, Django и проч. Об этом (и некотором сравнении с
Flask, API-роутерах, фишках с настройками) можно почитать в статье с
Хабра в разделе "Источники и доп. материалы".
________________________________________________________________________

### ОТДЕЛЬНЫЕ ПРИЛОЖЕНИЯ И МИКРОСЕРВИСЫ ###

Обычно микросервисная архитектура больше не вопрос фреймворков и проч.,
а вопрос настройки системы и архитектуры сервиса как такового. В случае,
если нужно разрабатывать проект с микросервисной архитектурой с нуля,
потребуется:

- `httpx` - для асинхронных HTTP-запросов м/ микросервисами.

    Пример:

    ```py
    ...
    async with httpx.AsyncClient() as client:
        response = await client.get('http://localhost:8001/some/endpoint')
    ...
    ```

    Как видно, в целом можно поднять и разные приложения на одном
    устр-ве на разных портах и заставить их общаться в рамках одной
    машины без доп. заморочек, но это неудобно, не изолированно и
    небезопасно.

- `Docker Compose` - запустить разные микросервисы в разных контейнерах,
    настроить общение м/ ними, а внутри кода обращение ч/ имя
    контейнера, а не localhost. Получаются действительно изолированные
    микросервисы с более удобным исп-ем.

- `Nginx` - reverse-прокси для единой точки входа (перенаправление
    запросов с одного единого порта сервера на нужные порты приложения
    на основе пути до эндпоинта).

Это самый простой и довольно распространенный способ.
